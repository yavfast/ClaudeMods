## 2. Domain Model  {#C_CTX_02}

### 2.1. Key Entities  {#C_CTX_02_01}

| Сутність | Відповідальність |
|----------|------------------|
| Розмова | Упорядкований список рядків основної сесії агента, від найстарішого до найновішого |
| Рядок | Одне повідомлення користувача або агента: текст, виклики інструментів, результати інструментів; рядок, який хост віддав без змін, несе маркер хоста і зберігається хостом як є |
| Пара виклику | Виклик інструменту в рядку агента та його результат у рядку користувача, пов'язані спільним ідентифікатором |
| Медіа-ресурс | Зображення (фото, скриншот) або документ (PDF тощо) в результаті інструменту чи в промпті людини; має тип і розмір |
| Опис медіа | Текст агента, що заміняє медіа-ресурс: що на ньому, витягнуті факти, посилання на оригінал в архіві |
| Правка | Одна зміна: стиснути результат разом з його медіа (summarize), прибрати пару (drop), згорнути діапазон рядків (collapse), переписати текст агента (rewrite), замінити медіа в промпті людини описом (describe) |
| Якір | Відбиток рядка, яким правка за індексом знаходить свій рядок, якщо розмова зсунулась |
| Черга правок | Правки сесії, що чекають застосування, разом із налаштуваннями продовження та звітом, ще не доставленим агенту; живе у файлі сесії |
| Архів | Файл з оригіналами змінених рядків, по одному на кожне застосування, і окремі файли з оригіналами замінених медіа-ресурсів |
| Звіт | Підсумок застосування: що застосовано, що ні, скільки місця звільнено, де архів |
| Текст заміни | Те, що стоїть на місці зміненого рядка чи результату: власна нотатка агента, сказана від його імені — його пізніший виклик правки замінив тут те, що він сам прочитав, і де лежить оригінал; без префікса мода ([C_CTX_DEC_25](#C_CTX_DEC_25)) |
| Рядок застосування | Один рядок для людини в стрічці після застосування, що щось змінило: скільки правок застосовано і скільки звільнено; модель його не бачить ([C_CTX_DEC_26](#C_CTX_DEC_26)) |
| Етап | Логічний блок рядків, яким агент позначає етап або фазу завдання: назва і початок; одночасно відкритий лише один, етапи не вкладаються. Реєстр пам'ятає відкритий етап і кінець останнього закритого — обидва як межу «після рядка» |
| Мітка оптимізації | Коротка самопояснювальна мітка в тексті відповіді агента: «блок етапу завершено, оптимізуй його на переході» |
| Блок, що чекає стискання | Блок, закритий міткою оптимізації; його назва і порада приходять агенту з наступним промптом людини і в результаті відкриття наступного етапу; перестає чекати після правки його рядків або відкриття наступного етапу ([C_CTX_DEC_30](./context_editor.methods.concept.md#C_CTX_DEC_30)) |
| Хід оптимізації | Хід, який мод запускає своїм промптом після `/compact` людини: агент стискає розмову сам; межі блоку й телеметрію показує перегляд |
| Телеметрія контексту | Відомості, які агент отримує на запит (у заголовку перегляду, окремо без рядків, і в результаті закриття етапу): розмір рядків розмови без незмінної частини (системного промпту, схем інструментів, навичок), незмінна частина, розмір відкритого етапу, скільки лишилось до вбудованої компактизації, кандидати авторозмітки, підсумок журналу ефекту |
| М'яке нагадування | Окремий рядок-пропозиція мода `[context-editor: suggestion]`: після результату великого виводу чи пошуку, коли розмова велика і з минулої пропозиції виросла, або з наступним промптом людини після серії таких виводів; називає дію (які виводи стиснути, чи закрити відкритий етап), що вона звільняє, скільки коштує кешу промпту і чи окупиться; нічого не ставить у чергу і не закриває — рішення лишається за агентом |
| Запис етапу | Підсумок, яким агент заміняє опрацьоване в блоці етапу: мета, рішення з причиною і цитатою людини, перевірені факти з джерелами, змінені артефакти, відкриті питання |
| Слот стану | Один текстовий рядок агента з тегом `state`: поточний стан роботи (рішення, параметри, наступний крок), який агент переписує на місці |
| Журнал ефекту | Файл сесії: що стиснуло кожне застосування і які вже стиснуті відтворювані виводи чи архіви оригіналів агент потім читав знову; скільки звільнено, вимірює телеметрія |
| Тег | Позначка рядка, діапазону рядків або пари виклику: `pin` (недоторканне), `disposable` з нотаткою-заміною, `review` (кандидат на чищення, з причиною), `state` (слот стану); може мати термін у ходах |
| Реєстр тегів | Теги сесії разом з лічильником завершених ходів; живе у файлі сесії поруч із чергою |
| Нотатка | Довільний службовий текст агента до рядка, діапазону рядків або пари виклику, з коротким ідентифікатором (`n3`); на одній цілі їх може бути кілька, вони не змінюють і не захищають рядок, як тег, а служать агенту: позначити кандидата на видалення, залишити нагадування, перехресне посилання. Може мати нагадування через задану кількість ходів. Живе в реєстрі тегів, поза повідомленнями |
| Вкладення хоста | Повідомлення, яке хост сам докладає до запиту (копія файлу інструкцій, перелік навичок, нагадування); не рядок розмови. Мод відповідає лише на копії файлів інструкцій і переліку: лишає, переписує застарілі розділи першої копії рядком «superseded» або пропускає застарілу копію; рішення — у файлі сесії ([C_CTX_DEC_22](#C_CTX_DEC_22)) |
| Правило тегування | Автоматичне правило мода, що спрацьовує в момент додавання рядка або виклику інструменту і ставить тег цьому рядку або раннім рядкам, які він робить застарілими чи дублікатами; копії рядків, які хост додає заново після компактизації (від імені розширення), правила не зачіпають |
| Псевдонім виклику | Короткий стабільний ідентифікатор виклику інструменту (`c17`), який мод показує агенту одразу після результату; агент адресує ним виклик у правках і тегах |
| Передача | Запит перенести поточну розмову в нову сесію одним зі способів — «транскрипт» або «документ»; живе в черзі правок і виконується після кінця ходу |
| Нова сесія | Звичайна сесія хоста, яку створює передача вбудованою командою очищення: мод засіває її очищеною розмовою з парами викликів через власну компактизацію (спосіб «транскрипт») або надсилає документ передачі першим промптом (спосіб «документ»); стара сесія лишається на диску повним архівом |

```
Розмова ──1:N── Рядок ──1:N── Пара виклику
   │              └──0:N── Медіа-ресурс ──0:1── Опис медіа
   │
   └── Черга правок ──1:N── Правка ──0:2── Якір
            │
            ├── Звіт (останній, не доставлений)
            ├── Реєстр тегів ──1:N── Тег ──1:1── Рядок, діапазон або Пара виклику
            │        ├──0:N── Нотатка ──1:1── Рядок, діапазон або Пара виклику
            │        ├──0:1── Етап (відкритий) ──1:1── межа «після рядка»
            │        └──0:1── кінець останнього закритого етапу (межа «після рядка»)
            ├── Журнал ефекту
            └── застосування ──1:1── Архів
```

### 2.2. Data Flows  {#C_CTX_02_02}

Потік правки:

```
Агент            Мод                                     Хост
  │ перегляд ───────▶│ рядки з початку                      │
  │ правки ─────────▶│ перевірити, у чергу                  │
  │ кінець ходу ───────────────────────────────────────────▶│
  │                  │◀─────────────────── хід завершено ───│
  │                  │── команда компактизації з міткою ───▶│
  │                  │◀──────────── обробник компактизації ─│
  │                  │ застосувати, архів, звіт; новий список ▶│
  │                  │── звіт + промпт продовження ────────▶│
  │◀───────────────────────────────────────── новий хід ───│
```

Потік оптимізації етапу:

```
Агент                       Мод                                   Хост
  │ відкрити етап «назва» ─▶│ межа після попереднього рядка         │
  │ ... робота етапу ...     │ авторозмітка нових рядків             │
  │ закрити етап ──────────▶│ межі блоку, телеметрія, порада;       │
  │                          │ заміни з disposable — у чергу         │
  │ одна правка блоку ─────▶│ у чергу                               │
  │ кінець ходу ───────────────────────────────────────────────────▶│
  │                          │ застосування, як у потоці правки     │

  │ відповідь з міткою «оптимізуй», кінець ходу ───────────────────▶│
  │                          │◀───────────────────── хід завершено ──│
  │                          │ закрити відкритий етап;               │
  │                          │ блок чекає стискання                  │
  │◀── наступний промпт людини + назва блоку і порада ──────────────│
  │ новий етап: правка блоку; кінець ходу ─────────────────────────▶│
  │                          │ застосування, як у потоці правки     │
```

Телеметрію агент отримує на запит — у заголовку перегляду, окремо без рядків і в результаті закриття етапу; після звичайних викликів інструментів мод нічого не додає.

Потік тегування:

```
Рядок додається ──▶ правила мода ──▶ реєстр (pin / review / disposable)
Агент ── context_tag ──────────────▶ реєстр
Етап закрито інструментом ──▶ заміни з disposable у чергу ──▶ кінець ходу ──▶ застосування
Мітка оптимізації ──▶ блок чекає ──▶ перехід: правка агента або новий етап ──▶ заміни з disposable у чергу ──▶ кінець ходу ──▶ застосування
```

## 3. Mechanisms  {#C_CTX_03}

### 3.1. Core Algorithm  {#C_CTX_03_01}

1. **Перегляд.** Агент отримує розмову сторінками від найстарішого рядка: індекс, роль, розмір, ідентифікатори викликів, короткий фрагмент, позначки «вже змінено», «великий» і «містить медіа» з типом і розміром кожного медіа-ресурсу.
2. **Постановка в чергу.** Агент передає пакет правок і, за бажанням, текст для продовження. Кожна правка перевіряється на поточній розмові; правки за індексом отримують якорі; неприйнятні правки повертаються з причиною. Прийняті правки дописуються до черги сесії.
3. **Кінець ходу.** Агент завершує хід короткою реплікою. Мод помічає непорожню чергу і запускає вбудовану команду компактизації зі своєю міткою; хост виконує її, щойно сесія вільна. Якщо хост відмовив, черга лишається, а причина видна в рядку стану.
4. **Застосування.** Обробник редактора розпізнає свою мітку, бере правки з черги, знаходить рядки (за ідентифікаторами пар або якорями), застосовує правки від кінця розмови до початку, відкидає правку, що перекривається з пізнішою, записує оригінали в архів і повертає хосту новий список рядків. Медіа-ресурси рядків, яких стосуються правки, мод бере з подання розмови у форматі запиту до моделі і зберігає окремими файлами до заміни; шляхи до них вписуються в опис. Змінена пара отримує новий ідентифікатор; рядки з результатами інструментів без медіа збираються наново, а незмінені рядки з медіа повертаються хосту як є; службові виклики самого мода прибираються. Текст заміни — власна нотатка агента від його імені: його пізніший виклик правки замінив тут те, що він сам прочитав, і де лежить оригінал; префікса мода він не має ([C_CTX_DEC_25](./context_editor.core.concept.md#C_CTX_DEC_25)).
5. **Продовження.** Після компактизації людина бачить у стрічці один рядок — скільки правок застосовано і скільки звільнено; модель його не бачить ([C_CTX_DEC_26](./context_editor.core.concept.md#C_CTX_DEC_26)). Далі мод надсилає звіт і текст продовження як новий промпт, і агент продовжує роботу з легшим контекстом. Якщо продовження вимкнено, звіт додається до наступного промпту людини.

### 3.3. Edge Cases  {#C_CTX_03_03}

| Ситуація | Поведінка |
|----------|-----------|
| Діапазон розриває пару виклику | Правка відхиляється і при постановці, і при застосуванні |
| Розмова зсунулась до застосування | Правка за індексом знаходить рядок за якорем; не знайшла — не застосовується, причина у звіті |
| Дві правки перекриваються | Застосовується та, що стоїть пізніше в розмові; інша — у звіті як неприйнята |
| Жодну правку не вдалося застосувати | Компактизація скасовується; справжнє підсумовування не запускається |
| Збій обробника | Компактизація з міткою редактора скасовується; справжнє підсумовування з обробника не запускається; черга очищується, звіт про збій доставляється агенту |
| Хост покинув компактизацію (людина перервала) | Розмова і черга не змінюються; пакет застосується після наступного ходу |
| Паралельні виклики з результатами в одному рядку, медіа в одному з них | Правка іншої пари відхиляється, поки медіа не замінено в тому самому пакеті |
| Згортання діапазону з промптом людини, коли в розмові є незіставлене медіа промптів | Відхиляється: таке медіа неможливо заархівувати ([SP_CTX_DEC_06](./context_editor.decisions-01.sp.md#SP_CTX_DEC_06)) |
| Файл черги пошкоджено | Наступна постановка правок переносить його вбік і починає з порожньої черги |
| Мод вимкнено, а черга непорожня | Компактизацію ніхто не запитує; черга лежить у файлі сесії і застосується після першого ходу, коли мод увімкнуть |
| Рядки команди компактизації з міткою мода | Лишаються в розмові: модель бачить команду з самопояснювальною міткою і позначку виконання |
| Файл оригіналів не вдалося записати | Жодна правка пакета не застосовується; звіт пояснює причину |
| `/clear` або `/resume` у тому самому процесі | Мод переходить до сховища нової сесії; черга попередньої не застосовується до нової розмови |
| Каталог мода не вдалося закрити від інших користувачів | Мод нічого не пише на диск: правки й теги відхиляються з причиною |
| Хід перервано | Черга зберігається до наступного завершеного ходу |
| Людина почала хід, поки команда компактизації чекала | Команда виконується після цього ходу; промпт продовження не надсилається — звіт іде з наступним промптом людини |
| Хост відхилив команду компактизації | Черга лишається; текст відмови хоста — у рядку стану |
| Одноразовий запуск `claude -p` | Мод нічого не застосовує: після останнього ходу сесії в процесі немає; черга чекає наступного запуску в підтримуваному хості |
| Перезавантаження мода | Черга і недоставлений звіт лежать у файлі сесії й не губляться |
| Виклик з субагента | Відмова з поясненням |
| Медіа не вдалося зберегти в архів | Правка, що замінює це медіа, не застосовується; медіа лишається в контексті, причина у звіті |
| Рядок промпту з медіа не зіставлено однозначно з поданням запиту | Позначки медіа немає, правка `describe` для нього відхиляється |
| Правка не стосується рядка з медіа | Рядок повертається хосту як є, медіа зберігається |
| Правка зачіпає рядок з тегом `pin` | Правка відхиляється з причиною; агент може зняти тег і повторити |
| Правка захоплює повідомлення людини (промпт або відповідь через інструмент запитань) | Правка приймається, але результат постановки називає ці рядки і радить лишити їх дослівно, якщо агент не робить цього свідомо ([C_CTX_DEC_21](./context_editor.core.concept.md#C_CTX_DEC_21)); за [C_CTX_DEC_34](./context_editor.curation.concept.md#C_CTX_DEC_34) і [C_CTX_DEC_38](./context_editor.curation.concept.md#C_CTX_DEC_38) таку правку в поточній сесії мод відхилятиме, і дозволу на неї немає (опис медіа дозволений) |
| Доставка хоста посеред ходу (повідомлення людини, набране під час ходу, звіт субагента, сповіщення фонової задачі): хост показує її моделі окремо від рядків і переносить через компактизацію лише разом з незміненим рядком результату, за яким вона висить | Мод записує її текст у мить появи і, коли застосування чи передача перезбирає цей рядок результату, вставляє доставку рядком одразу після нього; стиснення результату її лишає, згортання чи видалення результату забирає разом з ним — для повідомлення людини так само, як для інших її повідомлень: сьогодні з попередженням при постановці, а за [C_CTX_DEC_34](./context_editor.curation.concept.md#C_CTX_DEC_34) — з відмовою без команди людини ([SP_CTX_DEC_19](./context_editor.decisions-01.sp.md#SP_CTX_DEC_19), рішення розробника 2026-10-11; спайк [context_editor_attachments](./context_editor_attachments.spike.md)) |
| Доставка, якої мод не бачив (форк сесії, старіша сесія, доставка до завантаження мода) | Губиться при застосуванні, як і до цього; запасне читання файлу сесії — у backlog плану |
| Ціль тегу зникла (рядок змінено або прибрано) | Тег видаляється з реєстру при наступному застосуванні; межа етапу — переїжджає ([C_CTX_03_02](./context_editor.methods.concept.md#C_CTX_03_02)) |
| Етап закрито, а в блоці нема чого стискати | Агент нічого не ставить у чергу; якщо немає й тегів `disposable`, компактизації немає |
| Відкриття етапу при відкритому етапі | Поточний етап закривається з межами блоку і порадою, потім відкривається новий |
| Закриття без відкритого етапу | Відмова з поясненням; агент може відкрити етап, вказавши перший рядок блоку |
| Мітка оптимізації без відкритого етапу | Блок — рядки після кінця останнього закритого етапу або від початку розмови |
| Людина продовжує етап блоку, що чекає | Агент лишає блок як є; порада з промптом приходить лише з першим промптом після мітки; блок чекає далі, до відкриття наступного етапу чи правки його рядків ([C_CTX_DEC_30](./context_editor.methods.concept.md#C_CTX_DEC_30)) |
| Черга непорожня на кінці ходу з міткою (правки агента цього ходу) | Застосовується, як після звичайного ходу; мітка лише позначає блок, заміни з тегів `disposable` блоку чекають переходу |
| Друга мітка, поки попередній блок чекає | Блоки, що чекають, об'єднуються: порада називає діапазон від початку першого до кінця останнього |
| Мітка, після якої переходу немає (сесія скінчилася) | Нічого не стискається; передача і `/compact` людини працюють, як завжди |
| Закриття етапу інструментом і мітка в тому самому ході | Мітка стосується блоку щойно закритого етапу |
| Мітка у відповіді ходу оптимізації (`/compact` людини) | Не діє |
| Діапазон захоплює слот стану | Правка відхиляється з причиною, як для `pin` |
| Вбудована компактизація хоста (своя або людини) | Межа етапу, чий рядок уже не в поточній розмові, переїжджає на голову розмови (відкритий етап) або стає невідомою (кінець закритого: перегляд і телеметрія кажуть, що рядка кінця вже немає, а не що блок порожній; початок закритого блоку теж діє від голови); теги зниклих рядків, зокрема `state`, видаляються; про це сказано в наступному перегляді й телеметрії |
| Рядок межі етапу замінено правкою (стиснення, згортання, переписування, опис медіа) | Межа переходить на останній рядок, створений цією правкою: стиснутий кінець блоку лишається в ньому, наступний етап його не захоплює |
| Рядок межі етапу прибрано без заміни або змінено засівом | Межа переїжджає за найближчий попередній незмінений рядок, що лишився |
| Телеметрія недоступна: немає розбивки контексту, у ній немає рядка рядків розмови, або ще немає відповіді моделі (свіжа сесія, щойно після компактизації) | Телеметрія показує розмір усього запиту з позначкою, що незмінна частина в ньому, або «ще невідомо» |
| Рядок нотатки замінено правкою | Нотатка переходить на останній рядок, створений правкою, — як межа етапу |
| Рядок нотатки прибрано без заміни | Нотатка видаляється; звіт застосування називає видалені нотатки |
| Нагадування нотатки настало, а агент не викликає інструментів | Нагадування чекає наступного виклику інструменту в основній розмові |
| Очікування промпту всередині обробника | Заборонене: призводить до взаємного блокування, бо промпт стартує лише після компактизації |
| Відновлення сесії | Хост повертає оригінали відредагованих результатів ([C_CTX_DEC_05](./context_editor.core.concept.md#C_CTX_DEC_05)) |

### 3.4. Tagging Mechanism  {#C_CTX_03_04}

| Тег | Хто ставить | Що відбувається |
|-----|-------------|-----------------|
| `pin` | агент; мод — рядок документа передачі в новій сесії і підсумок засіву «транскриптом» | жодна правка (агента чи автоматична) не може змінити рядок; щоб змінити, агент спершу знімає тег — будь-який пін, коли має причину ([C_CTX_DEC_38](./context_editor.curation.concept.md#C_CTX_DEC_38)); автопіну першого промпту людини немає |
| `disposable` + нотатка | агент | коли агент закриває етап або просить оптимізацію, мод сам замінює вміст нотаткою (як `summarize` для пари, як `rewrite` для тексту агента, як `collapse` для діапазону); оригінал іде в архів |
| `review` + причина | агент; правила — великий вивід інструменту, вивід пошукових інструментів після кількох ходів, застаріле читання, дублікат | лише позначка для агента в перегляді, у телеметрії і в результаті закриття етапу; нічого не прибирається автоматично |
| `state` | агент | слот стану: інші правки рядка не змінюють, лише переписування; один на сесію |

Тег може мати термін у ходах: `review` з терміном стає видимим кандидатом лише після цієї кількості завершених ходів. `disposable` може позначити й діапазон рядків — гілку, яку агент щойно відкинув: найкращий момент записати, що з глухого кута варто лишити, — мить відмови, поки агент це пам'ятає.

Авторозмітка кандидатів (мод позначає, вирішує агент):

| Кандидат | Коли | Чому |
|----------|------|------|
| Застаріле читання | агент змінив файл інструментом редагування або запису, а раніше читав його | раннє читання описує вже не той файл — це питання правильності, а не лише місця |
| Дублікат | великий текст повторює вміст раннього рядка (той самий результат, той самий діапазон файлу; вставки хоста на зразок повторно завантаженої навички — лише якщо вони є рядками розмови, які мод читає: не перевірено, перевіряє живий сценарій специфікації) | ранню копію можна прибрати без втрат, якщо вміст не змінився: зміну файлу оболонкою правило не бачить ([C_CTX_06_08](./context_editor.curation.concept.md#C_CTX_06_08)) |
| Відтворюваність | кожна пара в перегляді позначена класом за інструментом: читання файлів і пошук — відтворювані, відповіді людини (зокрема відповіді на запитання агента через інструмент запитань — це повідомлення людини в результаті інструмента), живі проби, звіти субагентів, веб-вміст — ні | відтворюване можна стиснути до вказівника «що, де, що знайдено — перечитати за потреби», невідтворюване — лише обережним підсумком |

Тег `disposable` без нотатки не допускається: автоматично прибирати можна лише те, для чого агент уже записав заміну ([C_CTX_DEC_08](./context_editor.core.concept.md#C_CTX_DEC_08)).

Після застосування правок теги рядків, які змінилися, видаляються з реєстру: змінена пара отримує новий ідентифікатор, а її тег уже виконав свою роль. Виняток — `state`: переписаний слот стану лишається слотом, тег переходить на новий рядок.

### 3.5. Call Aliases  {#C_CTX_03_05}

Агент не бачить службових ідентифікаторів своїх викликів інструментів, тож щоб позначити або стиснути щойно прочитане, мусив спершу переглядати розмову. Тому мод одразу після результату виклику, який варто редагувати (великий вивід, результат пошуку), додає до нього короткий рядок з псевдонімом — `[context-editor] id c17`. Рядок дописується в момент створення результату, тож не скидає кеш і не змінює сам результат. Псевдонім — порядковий номер у межах сесії; мод зберігає відповідність «псевдонім → виклик». Правки і теги приймають ціль за псевдонімом, а `last` означає останній виклик агента в розмові, позначений чи ні, крім викликів інструментів самого мода ([SP_CTX_DEC_20](./context_editor.decisions-01.sp.md#SP_CTX_DEC_20); до фази 21 — останній позначений, і після малого виклику `last` мовчки вказував на старіший). Коли виклик стиснуто або прибрано, його псевдонім виконав роль і більше не діє. М'яке нагадування ([§3.2](./context_editor.methods.concept.md#C_CTX_03_02)) з фази 23 — окремий рядок після рядка псевдоніма, з власним префіксом (у фазі 22 воно заміняло рядок псевдоніма і починалося ним).

### 3.7. Service Notes  {#C_CTX_03_07}

Агент може додати до будь-якого попереднього рядка, діапазону рядків або пари виклику довільну службову нотатку ([C_CTX_DEC_20](./context_editor.core.concept.md#C_CTX_DEC_20)). Нотатка, на відміну від тегу, нічого не робить сама: не захищає рядок, не ставить заміни і не змінює розмову; на одній цілі їх може бути кілька. Як ними користуватися, вирішує агент: позначити одразу, що рядок можна видалити чи стиснути і як; лишити нагадування, що повернутися до виводу після перевірки; зв'язати рядки між собою. Нотатки живуть у реєстрі сесії, тож не коштують токенів і не скидають кеш, а агент бачить їх у перегляді поруч із рядками, у результаті закриття етапу і як число в телеметрії; промпт ходу оптимізації рядків не читає, тож лише відсилає до перегляду. Нотатка може мати нагадування через задану кількість завершених ходів: тоді мод один раз додає її текст до результату наступного виклику інструменту в основній розмові — так само, як рядок псевдоніма. Це свідоме нагадування агента самому собі, а не нагадування за розміром ([C_CTX_DEC_15](./context_editor.methods.concept.md#C_CTX_DEC_15)). Коли правка замінює рядок нотатки, нотатка переходить на рядок, створений правкою, як межа етапу ([C_CTX_03_02](./context_editor.methods.concept.md#C_CTX_03_02)); коли рядок прибрано без заміни, нотатка видаляється, і звіт застосування це називає. Передача переносить нотатки в нову сесію разом із тегами.

### 3.8. Host Attachments  {#C_CTX_03_08}

Окрім рядків розмови, хост сам докладає до запитів вкладення: файли інструкцій (CLAUDE.md, пам'ять, вкладені CLAUDE.md), перелік навичок, нагадування. Рядками вони не є — ні агент, ні правки їх не бачать, — але кожне лишається в кожному наступному запиті. Кожне застосування мода — компактизація, після якої хост перечитує файли інструкцій і з першим промптом після межі докладає **повну нову копію** кожного зміненого файлу («each replaces its earlier copy»), а старі копії лишаються; після відновлення сесії він ще раз докладає перелік навичок. У довгій сесії з частими правками CLAUDE.md так набирається чверть розмови (сесія d5614704: ≈ 45 тисяч токенів на запит).

Мод відповідає на ці вкладення через подію вкладення хоста: лишає, переписує або пропускає копію ([C_CTX_DEC_22](./context_editor.core.concept.md#C_CTX_DEC_22)). Розділ копії (один файл) застарілий, коли розмова вже має новішу іншу копію того самого файлу, або коли файл на диску відрізняється від найновішої копії файлу інструкцій — тоді хост докладе нову з наступним промптом (прогноз, що спирається на поведінку хоста: нову копію хост докладає лише після компактизації; файл, чия копія ще при першій появі не збігалась з диском, мод з диском не порівнює, а прогноз, який хост не справдив, знімає вже на першому кінці ходу і просить хост перепитати вкладення). Перша копія несе преамбулу («IMPORTANT: These instructions OVERRIDE…»), на яку посилаються пізніші, тож її мод лише переписує: застарілий розділ стає рядком «superseded by a later copy below», преамбула і живі розділи лишаються; решта цілком застарілих копій пропускається. Перелік навичок прибирається, лише коли новіший перелік називає всі його навички (пізніші переліки хоста інкрементні — лише додані навички), з побайтових повторів лишається перший. Невідомий формат, дельти, контекст хуків і вкладення субагентів мод не чіпає.

Хост питає вкладення не на кожен запит, а раз на процес — і ще раз усі після кожної компактизації та після відновлення сесії. Тому рішення мод ухвалює лише всередині власного застосування (кеш промпту там і так переписується, а хост одразу перепитає все, і стара копія зникає в тому самому запиті, де з'являється нова), а зберігає у файлі сесії: відновлений процес надсилає ті самі байти. Між застосуваннями нове вкладення лишається як є. З `keep_cache` вкладення замороженого префікса не змінюються. Звіт застосування і телеметрія називають, скільки копій лишено поза запитом і скільки це токенів.

### 3.10. Old Sessions  {#C_CTX_03_10}

Дані сесії — каталог сховища і каталог архівів у проєкті — потрібні, доки сесію можна відновити, тобто доки хост тримає її транскрипт ([C_CTX_DEC_29](./context_editor.core.concept.md#C_CTX_DEC_29)). Раз на добу на машину, у фоні після старту сесії, мод проходить сховища інших сесій: сесію без транскрипту видаляє разом з її архівами, а сесію, якої давно не торкались, пакує в `.zip` поруч з її каталогами. Коли запаковану сесію відкривають знову, мод розпаковує її до першого звернення до її файлів, тож шляхи в рядках замін знову ведуть на файли.

### 3.11. Passed-Over Hooks  {#C_CTX_03_11}

Мод залежить від базових можливостей хоста: хук `session.compact` за власною міткою (застосування, передача, ремонт), вкладення (`prompt.attachment`), двері `session.append`, контекст промпту (`prompt.submit`) і `$.command.run`. Хост 2.1.299+ з посадженим `cc-plugin-sec-default` пропускає частину з них у мода рівня `user` ([C_CTX_DEC_31](./context_editor.core.concept.md#C_CTX_DEC_31)); майбутні версії можуть змінити й інші. Тому раз на версію хоста мод перевіряє їх окремим процесом-зондом: на старті сесії, якщо для поточної версії результату немає, у фоні запускається `claude` з тим самим модом у тимчасовій теці, і зонд записує, які хуки до нього дійшли. Результат зберігається за версією хоста і діє з самого старту наступних сесій. Живі ознаки в сесії його переважають і оновлюють: вкладення дійшло — вкладення працюють; завершений хід без жодного вкладення — пропущено; команда мода, якої його обробник не побачив, — компактизацію пропущено.

Кожна можливість вимикає свою частину: без `session.compact` — `context_edit`, `context_handoff` і `/handoff` відмовляють з поясненням, Flush лишає чергу, ремонту немає, а голий `/compact` людини мод передає хосту з власними інструкціями підсумку (повідомлення людини й закріплені рядки дослівно, слот стану, записи етапів, нотатки, правки агента в черзі як бажані підсумки); без вкладень — відповіді про застарілі копії інструкцій; без дверей `session.append` — запис доставок і обрізання результатів субагентів. Людина бачить у чаті один рядок на процес: що вимкнено і як виправити (керований плагін). Поки зонд іде, дія, що запускає компактизацію мода, чекає його результату обмежений час; далі результат невідомий і дія дозволена (рішення розробника «Завжди дозволяти»). Ремонт після відновлення планується з кінця першого ходу процесу, коли результат відомий.

## 4. Integration Points  {#C_CTX_04}

### 4.1. Dependencies  {#C_CTX_04_01}

Інших концептів немає. Зовнішня залежність — хост Claude Code з API function hooks (версія ≥ 2.1.295, перевірено на 2.1.295 в інтерактивному терміналі і в неінтерактивному хості з потоковим входом — розширення VS Code; одноразовий `claude -p` поза обсягом):

| Фінальний текст ходу в події завершення ходу (перевірено лише в неінтерактивному хості з потоковим входом; термінал — живий сценарій специфікації) | мітка оптимізації |
| Читання розмови у форматі запиту до моделі (з блоками зображень і документів) | пошук медіа-ресурсів і збереження їх в архів |
| Розмір контексту останнього запиту і його розбивка за категоріями, як у `/context` | телеметрія контексту |
| Запуск вбудованої команди компактизації з міткою-аргументом від розширення | застосування правок, засів нової сесії |
| Навичка в складі розширення або додатковий контекст першого промпту | інструкція агенту на початку сесії про етапи, мітку і телеметрію |
| Відправка промпту від розширення | продовження після застосування, хід оптимізації (промпт без попередньої команди перевірено лише в неінтерактивному хості з потоковим входом; термінал — живий сценарій специфікації) |
| Читання і запис файлів, змінні середовища, ідентифікатор сесії | черга, архів |
| Рядок стану і спливні повідомлення | видимість для людини |
| Запуск вбудованої команди очищення від розширення, реєстрація власної команди | нова сесія, команда передачі для людини |
| Окремий запит до моделі над транскриптом сесії | документ передачі, коли агент його не дав |
| Подія додавання рядка з ідентифікатором субагента: переписаний текст нового результату інструмента зберігається і йде в запит | обрізання великих результатів субагента ([C_CTX_DEC_27](./context_editor.methods.concept.md#C_CTX_DEC_27)) |
| Подія вкладення хоста (`prompt.attachment`): текст вкладення, відповідь «лишити / переписати / пропустити», перепитування після компактизації і відновлення | застарілі копії файлів інструкцій і переліку навичок ([C_CTX_DEC_22](#C_CTX_DEC_22)) |
| Переписування аргументів команди в хуку `command.run` (`next({ ...e, args })`), що доходить до мода і при обході | `/compact` людини при обході: підсумок хоста за інструкціями мода ([C_CTX_DEC_31](#C_CTX_DEC_31)) |

### 4.2. API Surface  {#C_CTX_04_02}

- Для агента: інструмент перегляду розмови (з тегами), інструмент постановки правок у чергу та інструмент тегування ([SP_CTX_02_01](./context_editor.edits.sp.md#SP_CTX_02_01), [SP_CTX_02_02](./context_editor.edits.sp.md#SP_CTX_02_02), [SP_CTX_02_11](./context_editor.tags.sp.md#SP_CTX_02_11)).
- Для агента: етапи (відкрити, закрити) і слот стану в інструменті тегування; мітка оптимізації в тексті відповіді; телеметрія (з підсумком журналу ефекту) у заголовку перегляду, окремо без рядків і в результаті закриття етапу.
- Для агента: м'яке нагадування — окремий рядок-пропозиція після великого виводу або з наступним промптом людини після серії читань: дія, виграш, ціна кешу і вердикт вигідності; лише інформує.
- Для агента: інструмент нотаток — додати й зняти службову нотатку до рядка, діапазону чи пари виклику, з необов'язковим нагадуванням через кілька ходів; нотатки видно в перегляді, у результаті закриття етапу і в телеметрії.
- Для агента: інструмент передачі розмови в нову сесію з вибором способу ([SP_CTX_02_19](./context_editor.handoff.sp.md#SP_CTX_02_19)).
- Для людини: рядок стану з кількістю правок у черзі, спливне повідомлення зі звітом, промпт продовження від мода в стрічці розмови; команда передачі в нову сесію.
- Для людини: після кожного застосування, що щось змінило (і після передачі, засів якої застосував правки), — один рядок у стрічці: скільки правок і скільки звільнено; модель його не бачить ([C_CTX_DEC_26](#C_CTX_DEC_26)).
- Для агента: текст заміни — його власна нотатка від його імені, що називає його пізніший виклик правки, без префікса мода; службові тексти мода (звіти, псевдоніми, нагадування) префікс лишають ([C_CTX_DEC_25](#C_CTX_DEC_25)).
- Для людини: `/compact` без аргументів з модом — агент стискає розмову сам ходом оптимізації, повідомлення людини лишаються дослівно; `/compact host` — стандартний підсумок хоста; `/compact <інструкції>` — підсумок хоста з інструкціями людини ([C_CTX_DEC_23](./context_editor.methods.concept.md#C_CTX_DEC_23)).
- Для агента: аргумент власної `/compact` мода і речення кожного звіту застосування кажуть, що цю команду запустив мод, а не людина ([C_CTX_DEC_24](#C_CTX_DEC_24)).
- Для агента: речення звіту застосування і рядок телеметрії про застарілі вкладення хоста, лишені поза запитом ([C_CTX_DEC_22](#C_CTX_DEC_22)).
- Для агента субагента: великий результат інструмента (крім читання файлу) приходить головою і хвостом з рядком між ними — скільки символів вирізано і шлях повного виводу, який він відкриває інструментом читання файлів ([C_CTX_DEC_27](./context_editor.methods.concept.md#C_CTX_DEC_27)).
- На диску: файл черги сесії, файл реєстру тегів (з етапами), журнал ефекту, файл рішень про вкладення хоста, файли архіву оригіналів і файли замінених медіа-ресурсів у домашньому каталозі користувача; медіа-файли агент може відкрити інструментом читання файлів.

## Design Decisions

### DEC_01 — Яким механізмом хоста міняти збережену історію  {#C_CTX_DEC_01}

> **Status:** resolved
> **Date:** 2026-10-08

**Question:** Через яку подію хоста можна замінити рядки, які вже є в розмові?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| A — обробник компактизації повертає новий список рядків | працює для будь-якого рядка; лише між ходами; скидає кеш від першої правки |
| B — переписування рядка в момент додавання | змінює тільки новий рядок; агент ще не бачив вивід, тож не може вирішити, що з нього потрібно |
| C — переписування запиту на кроці моделі | повідомлення в цій події зафіксовані, змінювати їх не можна |

**Decision:** A.
**Rationale:** єдиний механізм, що змінює вже збережені рядки; перевірено наживо.
**Rejected because:** B — не дає редагувати після опрацювання; C — хост не дозволяє.

### DEC_02 — Хто запитує компактизацію  {#C_CTX_DEC_02}

> **Status:** resolved
> **Date:** 2026-10-08, переглянуто 2026-10-09

**Question:** Чи може одне розширення і запитувати компактизацію, і обробляти її?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| A — одне розширення з прямим запитом компактизації | хост пропускає обробники розширення для його власного прямого запиту; запускається справжнє підсумовування — підтверджено наживо; у неінтерактивному хості прямий запит відхиляється завжди |
| B — два розширення: редактор і тригер, прямий запит | працює лише в інтерактивному терміналі; між розширеннями потрібен спільний стан — файл черги, файл готовності, спільні константи |
| C — одне розширення, що запускає вбудовану команду компактизації зі своєю міткою | обробники ініціатора викликаються; працює в інтерактивному терміналі і в неінтерактивному хості з потоковим входом (спайк [context_editor_handoff_long](./context_editor_handoff_long.spike.md), 2.1.295); рядки команди з самопояснювальною міткою потрапляють у розмову |

**Decision:** C — розробник, 2026-10-09: компактизація «command.run всюди», тригер — «Об'єднати одразу».
**Rationale:** B не працює в розширенні VS Code (жива перевірка: правки лишилися в черзі); C працює всюди одним шляхом і прибирає спільний стан двох розширень.
**Rejected because:** A — обробник пропускається або запит відхиляється; B — не працює в неінтерактивному хості, зайвий протокол між розширеннями.

### DEC_03 — Коли застосовуються правки  {#C_CTX_DEC_03}

> **Status:** resolved
> **Date:** 2026-10-08

**Question:** Як агенту отримати відредагований контекст, якщо компактизація посеред ходу неможлива?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| A — правки в кінці ходу з автоматичним продовженням | агент завершує хід після постановки правок; мод повертає його до роботи промптом зі звітом |
| B — правки в кінці ходу без продовження | людина мусить сама продовжити сесію |

**Decision:** A за замовчуванням; B — за параметром правки.
**Rationale:** автономні задачі не мають зупинятися через чищення контексту. Хід оптимізації (з 2026-10-14 — лише за `/compact` людини, [C_CTX_DEC_30](./context_editor.methods.concept.md#C_CTX_DEC_30); до того — за міткою, [C_CTX_DEC_17](./context_editor.methods.concept.md#C_CTX_DEC_17)) — звичайний хід: продовження після нього задає правка агента, але за замовчуванням його немає: мітку ставлять, завершуючи хід для людини, тож пакет ходу оптимізації продовжує сесію, лише коли агент про це попросить ([SP_CTX_DEC_16](./context_editor.decisions-01.sp.md#SP_CTX_DEC_16), рішення розробника 2026-10-10).
**Rejected because:** B як типовий режим зупиняє автономну роботу.

### DEC_05 — Збереження правок після відновлення сесії  {#C_CTX_DEC_05}

> **Status:** open
> **Date:** 2026-10-08

**Question:** Як зробити так, щоб відновлена сесія бачила відредаговану, а не оригінальну історію?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| A — прийняти обмеження: правки діють у межах безперервної сесії | мод корисний для довгих безперервних сесій; після відновлення контекст повертається до оригіналу |
| B — дочекатися, поки хост позначатиме компактизацію від обробника так само, як вбудовану (рядок-підсумок і посилання на збережені рядки) | повне збереження; залежить від хоста |
| C — перенести очищену розмову в нову сесію, яку `--resume` відкриває як звичайну ([C_CTX_DEC_11](./context_editor.methods.concept.md#C_CTX_DEC_11), схема S — обрано) | збереження без зміни хоста для засіяної сесії; правки, зроблені в ній пізніше, знову живуть до відновлення |

**Decision:** OPEN — see resolution trigger. Діє A для звичайної сесії; C — через передачу ([C_CTX_DEC_11](./context_editor.methods.concept.md#C_CTX_DEC_11)), яка тепер засіває очищену сесію компактизацією, а не пише файл.
**Rationale:** компактизація від обробника — і прямим запитом, і командою — пише межу і копії повернених рядків; оригінали лишаються у файлі сесії перед межею. Відновлення йде по ланцюжку рядків від останнього до межі, і текстові правки, чиї відповіді повернено перезібраними цілими, переживають його; але воно може повернути оригінали двома шляхами: (а) копія рядка, поверненого з `handle` (особливо результат з медіа), має батька до межі, і все до останнього такого рядка вантажиться з оригіналів; (б) рядки асистента до межі з тим самим `message.id`, що й рядок, повернений з `handle`, підтягуються разом зі своїми результатами — виклики дублюються (спайк [context_editor_handoff_long](./context_editor_handoff_long.spike.md), Entry 6, 2.1.295, що замінює висновок Entry 3 E1; навичка plugin-hooks, пункт 7). API розширень не дає прибрати рядки з файлу сесії; надійний шлях — засів очищеної сесії, де перед межею немає нічого.
**Rejected because:** —
**Resolution trigger:** вихід версії Claude Code, у якій API компактизації дає позначити рядок-підсумок або в якій відновлення сесії поважає компактизацію від обробника; перевірка — інтеграційні сценарії [SP_CTX_05_03](./context_editor.scenarios.sp.md#SP_CTX_05_03) «Відновлення сесії (лише текст)» і «Відновлення сесії (медіа або злиття відповіді)».

### DEC_06 — Що робити з незміненими рядками, які містять медіа  {#C_CTX_DEC_06}

> **Status:** resolved
> **Date:** 2026-10-08

**Question:** Чи перезбирати рядки з результатами інструментів, що містять медіа, якщо правка їх не стосується?

**Options considered:**
| Option | Consequence |
|--------|-------------|

### DEC_09 — Залишковий ризик справжнього підсумовування  {#C_CTX_DEC_09}

> **Status:** resolved
> **Date:** 2026-10-08, переглянуто 2026-10-09

**Question:** Чи прийняти вікно до 15 с, у якому запит тригера може дійти до звичайної компактизації, якщо модуль редактора не перезавантажився, а хост лишив його інструменти зареєстрованими?

| Option | Consequence |
|--------|-------------|
| A — прийняти вікно (готовність = інструмент у процесі + файл готовності ≤ 15 с) | вікно виникає лише при невдалому гарячому перезавантаженні під час розробки мода; простий механізм |
| B — тригер просить редактор підтвердити готовність безпосередньо перед кожним запитом (файл-запит і відповідь) | вікно майже зникає; два записувачі сховища, опитування файлу, складніший протокол |
| C — один плагін замість двох | з прямим запитом неможливо ([C_CTX_DEC_02](#C_CTX_DEC_02), A); з командою компактизації можливо (DEC_02, C) |

Мод не запускає команду, якщо хід людини вже почався; лишається вікно в мить між перевіркою і постановкою в чергу, після якого ще мусить статися вивантаження або невдале перезавантаження мода посеред ходу — прийнятий ризик, як вікно варіанта A, але без файлу готовності.
**Rejected because:** A — вікно і файл готовності більше не потрібні; B — складність без потреби.

|--------|-------------|

### DEC_20 — Службові нотатки агента до рядків  {#C_CTX_DEC_20}

> **Status:** resolved
> **Date:** 2026-10-10

**Question:** Як дати агенту додавати довільні службові нотатки до попередніх повідомлень?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| A — окрема сутність «нотатка» в реєстрі сесії: кілька на ціль, з ідентифікатором і необов'язковим нагадуванням через кілька ходів; видно в перегляді, у результаті закриття етапу, у телеметрії; при правці рядка переходить на рядок заміни, при прибиранні — видаляється | нуль токенів, кеш не скидається; тег і нотатка не змішуються; ще один вид запису в реєстрі |

Думаю, що ai-агент придумає, як це можна використовувати. Наприклад, можна одразу помічати повідомлення, які можна видалити або оптимізувати, або додати нотатку для подальшої обробки, маркування або нагадування.» Нагадування — свідомий запит агента собі, а не нагадування за розміром ([C_CTX_DEC_15](./context_editor.methods.concept.md#C_CTX_DEC_15)).

### DEC_21 — Знахідки прогону на копії реальної сесії  {#C_CTX_DEC_21}

> **Status:** resolved
> **Date:** 2026-10-10

**Question:** Прогін мода на копії реальної сесії (~545 тисяч токенів, 11 згортань, ~539 → ~268 тисяч; `.dev_flow/cache/live-test/fork-test-results.md`) показав: оцінки розміру «символи на чотири» занижені в 2–5 разів; нагадування нотатки не приходить, якщо агент викликає лише інструменти мода; згортання діапазону непомітно поглинає відповіді людини через інструмент запитань, і підсумок губить дослівні цитати людини, що стояли за рішеннями. **Options considered:**
| Option | Consequence |
|--------|-------------|

| B — відхиляти правки, що захоплюють повідомлення людини | надійніше для цитат, але забирає в агента рішення, яке концепт йому лишає |
| C — нічого не міняти, лише описати в навичці | дешево; ті самі помилки повторюються |

| D — від імені агента, без позначки: текст заміни починається пізнішим власним викликом правки агента («Later, your context_edit summarize call replaced the full output you had read here with your own summary …»; заміна з тегу агента — його тегом, «Later, your context_tag disposable tag replaced …»); службові тексти мода префікс лишають | найкраще для обох моделей у спайку; ціна та сама, будова заміни та сама; розпізнавання замінених рядків переходить з префікса на набір відкривачів, старі тексти розпізнаються далі |

**Decision:** D — рішення розробника 2026-10-12: «Від імені агента, без позначки (Recommended)». Спайк — [context_editor_authorship](./context_editor_authorship.spike.md) (форма V6).
**Rationale:** агент вірить вмісту на місці результату як свідченню того, що там було (живий прогін фази 28: haiku визнав, що читав оригінал, у 6 з 9 прогонів замість 6 з 18, sonnet — 3 з 3; опис медіа — слабше, backlog); тож авторство і час мусять бути сказані саме там, словами, де підмет — агент і його власний виклик. Префікс мода перед цими словами відштовхує: haiku читає їх як слова плагіна. Будова заміни не змінюється, тож перевірки хоста лишаються в силі.
**Rejected because:** A — префікс підточує авторство; B і C — заглушка в слоті результату переконує модель, що вмісту не було, а C ще й дорожча й скидає кеш.

### DEC_26 — Що бачить людина після застосування  {#C_CTX_DEC_26}

> **Status:** resolved
> **Date:** 2026-10-12

**Question:** Застосування проходить між ходами: людина бачить хіба що спливне повідомлення, яке зникає, і промпт продовження з довгим звітом для агента. У неінтерактивному хості рядка стану й спливних повідомлень може не бути видно. Чи показувати людині, що застосування сталося і що воно дало, так, щоб це не потрапило в контекст моделі?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| A — нічого нового: спливне повідомлення і звіт у промпті продовження | людина не має сліду в стрічці; звіт написано для агента |
| B — рядок у стрічці, якого модель не бачить: після кожного застосування, що щось змінило, — скільки правок і скільки звільнено | слід лишається в стрічці; модель його не отримує, тож контекст не росте; у терміналі рядок зберігається і після відновлення сесії, у неінтерактивному хості — лише подія, як її покаже клієнт |
| C — рядок у розмові | модель бачила б його і платила б за нього токенами; дублює звіт |

**Decision:** B — рішення розробника 2026-10-12: «Так (Recommended)». Канал хоста — проба `$.ui.log` (навичка plugin-hooks, пункт 62).
**Rationale:** людині корисно бачити, що мод зробив з її розмовою і скільки це дало, а модель цього не потребує: її звіт приходить окремо.
**Rejected because:** A — без сліду для людини; C — платить контекстом моделі за текст для людини.

### DEC_28 — Де лежать архіви основної розмови  {#C_CTX_DEC_28}

> **Status:** resolved
> **Date:** 2026-10-13

**Question:** Рядок заміни каже агенту відкрити оригінал інструментом читання файлів (`original: <path>, open with Read`, [C_CTX_DEC_18](#C_CTX_DEC_18)), але архів лежить у сховищі мода `~/.claude/context-editor/<session_id>/`, поза проєктом, і хост без дозволу людини таке читання відхиляє (у терміналі — питає). Де мають лежати архіви основної розмови?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| 1 — у робочому каталозі сесії, поруч з архівами субагентів: `<cwd>/.claude/context-editor/<session_id>/` | читання без дозволу, як у субагентів; один каталог архівів сесії; мод створює `.claude/context-editor/` у проєкті |
| 2 — лишити в сховищі мода, дозволяти читання хуком `tool.check` | архіви поза проєктом; мод сам вирішує про дозволи хоста — ширше втручання |
| 3 — лишити як є | у неінтерактивному хості стиснуте недоступне |

**Decision:** 1 — розробник 2026-10-13: «можливо, архіви основної розмови теж потрібно перенести у каталог проєкту?», після пропозиції — «комітити фазу 34 і переходити до фази 35».
**Rationale:** той самий мотив і той самий каталог, що в [C_CTX_DEC_27](./context_editor.methods.concept.md#C_CTX_DEC_27). Переїжджає лише те, що агент відкриває: оригінали й медіа застосувань, передачі та відновлення після resume. Стан мода (черга, теги, журнал, засів передачі) лишається в сховищі: агент його не читає. Без робочого каталогу або коли каталог не створюється, архів пишеться у сховище, як раніше: застосування не залежить від проєкту. Старі архіви не переносяться: рядки старих замін несуть свої шляхи.
**Rejected because:** 2 — мод перебирав би рішення про дозволи хоста; 3 — лишає дефект.
**Оновлено 2026-10-21:** «робочий каталог сесії» — тепер корінь проєкту сесії `$.session.root()`: робочий каталог `$.session.cwd()` іде за `cd` оболонки агента, і архіви опинялись у підтеці чи в чужому клоні ([SP_CTX_DEC_45](./context_editor.decisions-21.sp.md#SP_CTX_DEC_45), фаза 47); варіант 1 і його мотив — без змін.

### DEC_29 — Що робити з даними старих сесій  {#C_CTX_DEC_29}

> **Status:** resolved
> **Date:** 2026-10-13

**Question:** Мод лишає по каталогу на кожну сесію у `~/.claude/context-editor/` (за 5 днів розробки — 296 сесій, 68 МБ) і, з фаз 34–35, каталог архівів у проєкті. Ніщо їх не прибирає. Коли дані сесії стають зайвими, хто їх прибирає і чи пакувати живі, але давно не відкриті?

**Options considered:**
| Option | Consequence |
|--------|-------------|
| Строк: разом із транскриптом хоста | хост сам видаляє транскрипти, старші за `cleanupPeriodDays`; без транскрипту сесію не відновити, тож її дані нікому не потрібні; поки транскрипт є, заміни після `--resume` ведуть на живі архіви |
| Строк: власний вік мода | звільняє місце швидше, але відновлена стара сесія втрачає архіви й теги |
| Запуск: автоматично / команда / обидва | автоматично — нічого не забути; команда — контроль людини |
| Пакування давно не відкритих: ні / `.zip` | `.zip` — менше місця на диску; агент не прочитає запакований архів, тож мод мусить розпакувати сесію до звернення до неї |

**Decision:** розробник 2026-10-13 (відповіді на питання): строк — «Разом із транскриптом (Recommended)»; запуск — «Лише автоматично»; пакування — «Пакувати в .z або .zip, щоб працювало потенційно на всіх платформах. При очистці основних сесій - видаляти разом з архівами».
**Rationale:** дані сесії живуть, доки сесію можна відновити. Мод раз на добу на машину, у фоні після старту сесії, видаляє сховище й каталог архівів сесій без транскрипту, а сховище й каталог архівів сесій, яких не торкались PACK_IDLE_MS, пакує в `.zip` (формат, який читають `unzip` і `bsdtar` — штатний `tar` macOS і Windows 10+). Запаковану сесію мод розпаковує в підготовці сховища, тобто до першого звернення мода чи агента: `--resume`, `/resume`, повернення до сесії, відкритої в процесі. Без інструмента пакування мод лише видаляє.
**Rejected because:** власний вік — губить архіви сесій, які хост ще дає відновити; команда — розробник обрав «Лише автоматично».

### DEC_31 — Коли хост обходить хуки мода  {#C_CTX_DEC_31}

> **Status:** resolved
> **Date:** 2026-10-14

**Question:** На хості 2.1.299+ з облікового запису Team/Enterprise або з керованими налаштуваннями вбудований `cc-plugin-sec-default` пропускає хуки `session.compact`, `prompt.attachment` і частину дверей `session.append` у плагіна рівня `user` (дослідження `.dev_flow/cache/live-test/host-2.1.299-bypass.md`). Тоді застосування черги, `/compact` людини, засів передачі й ремонт стають справжнім підсумком хоста, що порушує [C_CTX_DEC_09](#C_CTX_DEC_09). Як моду це виявити і що робити: (а) сигнал; (б) реакція інструментів; (в) повідомлення людині; (г) `/compact` людини; (д) стан «ще невідомо».

**Options considered:**
| Option | Consequence |
|--------|-------------|
| (а) A — поведінка: у цьому екземплярі модуля хід почався, а жоден `prompt.attachment` до мода не дійшов | перевірено зондом 2026-10-14: `--plugin-dir` на 2.1.296 — 11 викликів за хід, на 2.1.299 з посадженим модулем — 0, `turn.start`/`turn.complete` доходять на обох; перелік навичок приходить щоходу, бо навичка мода є завжди; не залежить від назви модуля і версії |
| (а) B — порядок модулів у `engine.create` (`e.plugins`) | керований мод стоїть після `sec-default` так само, як мод рівня `user`: порядок їх не розрізняє |
| (а) C — версія хоста ≥ 2.1.299 | не знає, чи посаджено модуль і чи мод керований |
| (а) D — перевірка можливостей окремим процесом-зондом раз на версію хоста: мод на старті сесії, якщо для поточної версії результату ще немає, у фоні запускає `claude` з самим собою в тимчасовій теці, і зонд перевіряє кожну базову можливість (хук `session.compact` за міткою мода, вкладення, двері `session.append`, контекст `prompt.submit`, `$.command.run`); результат зберігається за версією; живі ознаки в сесії його переважають (вкладення дійшло — працює; хід без вкладень — пропущено; команда мода, якої обробник не бачив, — пропущено) | бачить пропуск будь-якого хука до першого використання, без справжнього підсумку в розмові людини; кожну можливість вимикає окремо; коштує запит моделі й кілька секунд раз на версію; потребує спайка (запуск процесу з хука, той самий рівень завантаження мода, команда після ходу в дочірньому хості) |
| (б) відмова `context_edit`, `context_handoff`, `/handoff` з поясненням; Flush і ремонт без компактизації, черга лишається | агент бачить причину; справжній підсумок за міткою мода не запускається |
| (в) A — один рядок людині (`$.ui.log`) на процес при першому виявленні: причина і як виправити (керований плагін) | людина знає, чому стискання не працює |
| (в) B — лише у відмовах агенту | людина може не дізнатися |
| (г) A — підсумок хоста з рядком людині | працює як без мода |
| (г) B — відмова з рядком | людина мусить вводити `/compact host` |
| (г) C — голий `/compact` людини мод передає хосту як `/compact <інструкції мода>` (`next({ ...e, args })` у `command.run`, що доходить до мода): підсумок хоста за вказівками того, що мод знає — дослівно лишити повідомлення людини й закріплені рядки, текст слоту стану, записи етапів і нотатки; правки агента в черзі — як бажані підсумки їхніх діапазонів | підсумок хоста, але зберігає те, що агент уже вирішив; розмір інструкцій обмежений; власні аргументи людини не змінюються |
| (д) A — за версією: до 2.1.299 дозволяти, з 2.1.299 відмовляти | `/handoff` одразу після `--resume` на 2.1.299 відмовить |
| (д) B — завжди відмовляти | відмова і на 2.1.296 |
| (д) C — завжди дозволяти | ризик справжнього підсумку, якщо першою дією процесу на обхідному хості буде дія людини |

**Decision:** (а) D — розробник 2026-10-14 після першого вибору A: «Версію перевіряти не потрібно, але, можливо, у майбутніх версіях Claude Code може щось змінитися. Тому, при старті мода можна виконати перевірку роботи базових інструментів редагування контексту. Якщо якийсь інструмент перестав працювати, то відповідний функціонал мода можна відключити та вивести про це повідомлення у чаті. Таку перевірку можна роботи раз на версію.»; спосіб перевірки компактизації — «Окремий процес-зонд»; збережений результат — «Версія + живі ознаки (Recommended)»; A лишається живою ознакою; поки зонд іде, дії мода, що запускають компактизацію, чекають його результату обмежений час, далі — (д); (б) як описано, але окремо для кожної можливості; (в) A — розробник 2026-10-14: «Один раз на процес (Recommended)»; (д) C — розробник: «Завжди дозволяти» — для дій людини й агента; автоматичний ремонт після відновлення (планується від старту сесії, до будь-якого ходу) чекає відомого вердикту — переноситься на кінець першого ходу процесу, бо інакше він першим запустив би справжній підсумок; (г) — на запитання «Що робити з `/compact`…» розробник відповів запитанням «Чи можна у `compact` додати розширену інструкцію?»: так, хост дає переписати аргументи; рекомендація — C; розробник погодив («Ok»).
**Rationale:** сигнал за поведінкою відповідає самій причині (хуки не доходять), а не її ознакам, тож переживе зміну назви модуля, версії чи правил посадки; керований мод (спайк 2026-10-14, сесії `42b7f02c`, `8d5d677b`) отримує вкладення і працює повністю. Відмова замість підсумку тримає інваріант DEC_09.
**Rejected because:** (а) A як єдиний сигнал — не бачить пропуску лише `session.compact` до першого справжнього підсумку; (а) B — не розрізняє керований мод; (а) C — не знає про посадку, і розробник не хоче перевірки версії; (в) B — людина без пояснення; (д) A, B — вибір розробника.
