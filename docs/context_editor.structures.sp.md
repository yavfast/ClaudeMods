## 01. Data Structures  {#SP_CTX_01}

> Implements: [C_CTX_02](./context_editor.core.concept.md#C_CTX_02)

Нотація типів абстрактна: `string`, `int`, `bool`, `list<T>`, `map<K, V>`, `set<T>`, `json` (будь-яке значення JSON), `T?` — необов'язкове поле без значення за замовчуванням. «Розмір» тексту — кількість символів.

### 01_01. Row  {#SP_CTX_01_01}

Рядок розмови в поданні хоста. Хост віддає не більше ROW_WINDOW останніх рядків; індекс 0 — найстаріший доступний рядок.

Fields:
| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| role | `user` \| `assistant` | yes | — | — | Хто написав рядок |
| text | string | yes | `""` | — | Текстові блоки рядка, з'єднані |
| toolUses | list<ToolUse> | yes | `[]` | лише в рядку `assistant` | Виклики інструментів |
| toolResults | list<ToolResult>? | no | — | лише в рядку `user` | Результати інструментів |
| handle | string? | no | — | непрозорий; ставить лише хост | Присутній — хост зберігає рядок як є (з thinking-блоками і медіа); відсутній — хост збирає рядок лише з полів вище |

ToolUse:
| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| tool_use_id | string | yes | — | непорожній | Ідентифікатор виклику |
| tool | string | yes | — | непорожній | Повна назва інструменту |
| input | map<string, json> | yes | `{}` | — | Аргументи виклику |
| text | string? | no | — | — | Результат, як його прочитала модель; у зміненому виклику відсутній |

ToolResult:
| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| tool_use_id | string | yes | — | збігається з викликом | Ідентифікатор виклику |
| text | string | yes | `""` | — | Текстові блоки результату |
| isError | bool | yes | false | — | Результат — помилка |

Row не містить зображень і документів; їх знаходить [SP_CTX_02_10](./context_editor.edits.sp.md#SP_CTX_02_10).

Invariants:
- Кожному `tool_use_id` у `toolUses` відповідає рівно один ToolResult з тим самим ідентифікатором у пізнішому рядку, і навпаки.
- `size(row)` = довжина `text` + довжина серіалізованого `input` кожного виклику + довжина `text` кожного результату.

### 01_02. Edit  {#SP_CTX_01_02}

> **Курування:** операція `state` — [SP_CTX_01_30](./context_editor.curation.sp.md#SP_CTX_01_30).

Правка, як її передає агент. Варіант визначає поле `op`; кожне поле варіанта обов'язкове.

| op | Поля | Значення |
|----|------|----------|
| `summarize` | `tool_use_id: string` або `ref: string`, `summary: string` | Замінити результат виклику на `summary`; медіа цього результату замінюється разом з текстом |
| `drop` | `tool_use_id: string` або `ref: string` | Прибрати виклик і його результат разом з медіа |
| `collapse` | `from_index: int`, `to_index: int`, `summary: string` | Замінити рядки `from_index..to_index` (включно) одним підсумком |
| `rewrite` | `index: int`, `text: string` | Замінити текст рядка агента без викликів інструментів |
| `describe` | `index: int`, `description: string` | Замінити медіа в рядку промпту людини описом; текст промпту зберігається дослівно |

Обмеження: `summary`, `text`, `description` — непорожні після обрізання пробілів, не довші за MAX_TEXT. Для `summarize` і `drop` задається рівно одне з `tool_use_id` і `ref`; `ref` — псевдонім виклику або `last` ([SP_CTX_02_17](./context_editor.tags.sp.md#SP_CTX_02_17)), у черзі правка зберігається вже з `tool_use_id`. Індекси — позиції в переліку [SP_CTX_02_01](./context_editor.edits.sp.md#SP_CTX_02_01).

### 01_03. QueuedEdit  {#SP_CTX_01_03}

> **Курування:** `quoted`, `changes` — [SP_CTX_01_30](./context_editor.curation.sp.md#SP_CTX_01_30).

Edit плюс `anchors: list<string>?` — відбитки рядків для правок за індексом: для `collapse` — `[fingerprint(row[from_index]), fingerprint(row[to_index])]`, для `rewrite` і `describe` — `[fingerprint(row[index])]`, для правок за ідентифікатором — відсутні.

`via: "tag"?` (фаза 28) — заміна тегу `disposable`, яку поставив у чергу QueueTagReplacements ([SP_CTX_02_13](./context_editor.tags.sp.md#SP_CTX_02_13)): її текст називає `context_tag`, а не `context_edit` ([SP_CTX_02_04](./context_editor.edits.sp.md#SP_CTX_02_04)); інших значень немає (parseQueue відхиляє правку з іншим `via`), правки агента поля не мають.

`fingerprint(row)` = `role` + `|` + ідентифікатори викликів (`u:<id>`) і результатів (`r:<id>`) через кому + `|` + перші 160 символів `text`.

### 01_04. Queue  {#SP_CTX_01_04}

Файл `<storage>/pending.json` ([SP_CTX_01_07](#SP_CTX_01_07)). Читає і пише лише мод; кожен запис іде послідовним ланцюжком черги.

Fields:

|-------|------|----------|---------|-------------|-------------|
| edits | list<QueuedEdit> | yes | `[]` | ≤ MAX_QUEUE_EDITS (перевіряє і розбір файлу); серіалізований файл ≤ MAX_QUEUE_BYTES (перевіряють записи `context_edit` і QueueTagReplacements, не розбір: звіти можуть дописуватись) | Правки поточного пакета |
| resume | bool | yes | true | — | Продовжувати сесію після застосування поточного пакета. У ході оптимізації (`optimizePrompted = true`), поки агент не обрав продовження (`resumeSet = false`), виклик `context_edit` без `resume` ставить `false`, а з непорожнім `resume_prompt` — `true` ([SP_CTX_02_02](./context_editor.edits.sp.md#SP_CTX_02_02), [SP_CTX_DEC_16](./context_editor.sp.md#SP_CTX_DEC_16)) |

| tagsOnly | bool | yes | false | — | Пакет складається лише із замін з тегів |

| report | string? | no | — | — | Недоставлені звіти застосувань, з'єднані переносом рядка |
| reportId | int? | no | — | є тоді й лише тоді, коли є `report` | Час застосування, мс від епохи; ідентифікує звіт |
| reportResume | bool | yes | false | — | Після цього звіту потрібно продовжити сесію |
| reportPrompt | string | yes | DEFAULT_RESUME | ≤ MAX_TEXT | Текст продовження для цього звіту |
| handoff | HandoffRequest? | no | — | [SP_CTX_01_15](#SP_CTX_01_15) | Запит передачі в нову сесію; поки він є, правки черги належать передачі |
| optimize | bool | yes | false | — | Запит ходу стискання `/compact` людини ([SP_CTX_02_42](./context_editor.stages.sp.md#SP_CTX_02_42)) чекає Flush ([SP_CTX_02_06](./context_editor.edits.sp.md#SP_CTX_02_06)) або промпту людини ([SP_CTX_02_08](./context_editor.edits.sp.md#SP_CTX_02_08)); з 2026-10-14 буває лише з `compact` ([SP_CTX_DEC_37](./context_editor.sp.md#SP_CTX_DEC_37)): мітка оптимізації черги не змінює. Файл попередньої версії з `optimize` без `compact` розбирається; Flush і DeliverReport знімають такий запит без ходу і без поради |
| optimizePrompted | bool | yes | false | — | Промпт ходу оптимізації увійшов: мітку у відповіді наступного ходу основної розмови (ходу оптимізації) DetectOptimize ігнорує і знімає прапорець ([SP_CTX_02_30](./context_editor.stages.sp.md#SP_CTX_02_30)); промпт людини між ходами теж його знімає ([SP_CTX_02_08](./context_editor.edits.sp.md#SP_CTX_02_08)) — запобіжник петлі |
| compactEndedAt | int? | no | — | ≥ 0, мс | Коли скінчився хід стискання `/compact` людини (DetectOptimize, не перерваний); Flush його кінця ще не виконано. `/compact` у цей час — COMPACT_BUSY, поки Flush заплановано або минуло ≤ FLUSH_STALE від кінця ([SP_CTX_02_42](./context_editor.stages.sp.md#SP_CTX_02_42); живий сценарій 8). Знімають Flush, коли виконується, і новий запит; поза вікном без Flush нічого не вирішує |
| compact | bool | yes | false | — | Запит (`optimize`) або хід (`optimizePrompted`) — це `/compact` людини ([SP_CTX_02_42](./context_editor.stages.sp.md#SP_CTX_02_42)): уся розмова, промпт CompactTurnText, закритий блок не потрібен. Без `optimize` чи `optimizePrompted` не буває (розбір відхиляє); знімається разом із ними (DetectOptimize, DropOptimize, Settle). Файл без поля (до фази 25) читається як `false` |

Стан файлу при читанні: `missing` (файлу немає — значення за замовчуванням), `ok`, `unreadable` (не читається, не розбирається, будь-яке поле має не свій тип або порушує обмеження з таблиці: `edits` > MAX_QUEUE_EDITS, `resumePrompt` порожній чи > MAX_TEXT, `reportPrompt` > MAX_TEXT, `report` без `reportId` чи навпаки, `handoff` з порушенням [SP_CTX_01_15](#SP_CTX_01_15), зокрема `resumePrompt` > MAX_TEXT; аудит PL_AUD_CTX, CF-7 — тексти продовження йдуть моделі як промпт). `unreadable` ніколи не трактується як порожня черга.

Invariants:
- `resume`, `resumePrompt`, `resumeSet`, `tagsOnly`, `keepCache` стосуються лише поточного пакета і скидаються до значень за замовчуванням разом з ним: під час застосування, у гілці збою і в HandedOff ([SP_CTX_02_21](./context_editor.handoff.sp.md#SP_CTX_02_21)). Кожен запис, що закінчує пакет, будує чергу одним кроком KeepOtherSteps (пакет і його вибори — за замовчуванням; поля інших кроків — `optimize`, `optimizePrompted`, `handoff` — і недоставлений звіт — як прочитано), а звіт дописує AppendReport (новий звіт після недоставленого, `reportId` і продовження — нового звіту); нове поле Queue досить віднести до пакета чи до іншого кроку в одному місці (аудит PL_AUD_CTX, CF-6). Заміна Flush `optimize` → `optimizePrompted` ставить `resume = false`, `resumeSet = false` пакету, що лишився в черзі (його компактизацію покинуто), — продовження вирішує хід оптимізації ([SP_CTX_02_06](./context_editor.edits.sp.md#SP_CTX_02_06)).
- `report` і непорожній `edits` можуть існувати одночасно: звіт стосується попереднього пакета.
- `optimize` і `optimizePrompted` не бувають `true` одночасно: Flush заміняє `optimize = true` на `optimizePrompted = true` одним записом (порівняння-і-запис: лише коли `optimize` ще `true`) перед відправкою промпту ходу оптимізації і робить зворотну заміну, якщо промпт відхилено ([SP_CTX_02_06](./context_editor.edits.sp.md#SP_CTX_02_06)); `optimizePrompted` знімає кінець наступного ходу основної розмови (DetectOptimize) або промпт людини між ходами.
- Поки є `handoff`, `optimize` не стає `true` ([SP_CTX_02_42](./context_editor.stages.sp.md#SP_CTX_02_42)).
- Новий запис ставить `optimize = true` лише разом із `compact = true` (RequestCompact); `optimize` без `compact` лишається тільки у файлі попередньої версії ([SP_CTX_DEC_37](./context_editor.sp.md#SP_CTX_DEC_37)).
- Поля `optimize`, `optimizePrompted` і `compact` змінюють лише DetectOptimize, Flush (Optimize), DeliverReport і хук `/compact` людини ([SP_CTX_02_42](./context_editor.stages.sp.md#SP_CTX_02_42): RequestCompact пише `optimize = true`, `optimizePrompted = false`, `compact = true` одним записом; повертає їх як прочитано, якщо хук покинуто чи хост відхилив таймер).

### 01_05. ApplyReport  {#SP_CTX_01_05}

| Field | Type | Description |
|-------|------|-------------|
| applied | list<string> | ≤ MAX_QUEUE_EDITS. Описи застосованих правок (`summarize <id>`, `drop <id>`, `collapse #a..#b`, `rewrite #i`, `describe #i`) — за ціллю в черзі, тобто за індексами до застосування; за цими рядками HandleCompaction і BuildSeed звіряють застосовані правки з пакетом, тож FormatReport їх не змінює, а лише доповнює в тексті (нижче) |
| failed | list<string> | ≤ MAX_QUEUE_EDITS. Опис неприйнятої правки з причиною |
| charsBefore | int | Сума `size` рядків до застосування |
| charsAfter | int | Сума `size` рядків після застосування і [SP_CTX_02_05](./context_editor.edits.sp.md#SP_CTX_02_05) |
| originals | list<{ edit: string, rows: list<Row> }> | ≤ MAX_QUEUE_EDITS записів, рядків не більше, ніж у розмові. Оригінали змінених рядків для архіву |
| produced | list<{ edit: string, index: int, fingerprint: string }> | ≤ MAX_QUEUE_EDITS. Для кожної застосованої правки, що заміняє рядки (`summarize`, `collapse`, `rewrite`, `describe`), — опис правки, індекс і відбиток останнього рядка, який вона створила (рядок результату пари для `summarize` і `collapse` з носієм, єдиний рядок підсумку для `collapse` без носія, переписаний рядок для `rewrite` і `describe`), у **кінцевому** списку: після DropOwnCalls і KeepResponsesWhole у компактизації, після нормалізації засіву в BuildSeed. Рядок, якого в кінцевому списку вже немає, запису не має. Рахує Produced нижче; читає RebindTags для меж етапів ([SP_CTX_02_14](./context_editor.tags.sp.md#SP_CTX_02_14)) |
| notesDropped | list<string> | ≤ MAX_NOTES. Ідентифікатори нотаток, чиї рядки це застосування прибрало без заміни (RebindTags, [SP_CTX_02_14](./context_editor.tags.sp.md#SP_CTX_02_14)); заповнюється після RebindTags |
| ownCallsRemoved | int | ≥ 0. Скільки власних викликів мода (пар) прибрав DropOwnCalls ([SP_CTX_02_05](./context_editor.edits.sp.md#SP_CTX_02_05)) у списку, який замінює розмову; 0 — не прибрано жодного |
| mediaFiles | list<string> | ≤ кількості медіа-блоків у видимому вікні (≤ ROW_WINDOW повідомлень). Шляхи медіа-файлів, збережених цим застосуванням; для засіву ([SP_CTX_02_22](./context_editor.handoff.sp.md#SP_CTX_02_22)) — і медіа замінених пар, і медіа, перенесеного файлами |
| deliveries | `{ inserted: int, removed: int, unreadable: string? }` | `inserted`, `removed` ≥ 0. Доставки хоста посеред ходу ([SP_CTX_01_22](#SP_CTX_01_22)), які InsertDeliveries ([SP_CTX_02_36](./context_editor.stages.sp.md#SP_CTX_02_36)) вставило рядками (`inserted`) і які пішли разом із рядком-якорем, що його правка прибрала чи згорнула (`removed`); `unreadable` — причина, коли файл доставок не прочитався і вставок не було. Заповнюється після ApplyEdits (фаза 20) |
| pulledDropped | int | ≥ 0 (фаза 32). Скільки підтягнутих після `--resume` оригіналів застосування прибрало DropPulled перед правками ([SP_CTX_02_45](./context_editor.resume.sp.md#SP_CTX_02_45)); 0 — у тому самому процесі завжди. Коли > 0, FormatReport дописує речення PULLED_TEXT останнім перед CommandNote |

Текстовий звіт — `FormatReport(report, archive, kind)`, `kind` = `compaction` | `seed`; форма залежить від того, чи застосовано хоч одну правку:
- `applied` непорожній: `context-editor: applied N edit(s): <applied with NowIndex>. Not applied: <failed>. Conversation ~<before> -> ~<after> chars (estimate: <Estimate(before − after, ratio)> freed; context_list telemetry shows the measured change after the next response). Originals archived at <path>. Media archived: <paths>.` Число звіту — оцінка за символами; справжню зміну вимірює телеметрія (`Last apply`, [SP_CTX_02_28](./context_editor.stages.sp.md#SP_CTX_02_28)): прогін на копії сесії дав оцінку на 46 % вищу за виміряну зміну (рев'ю 39)
- `applied` порожній, `kind = compaction`: `context-editor: no edit was applied; the conversation was not changed. Not applied: <failed>.` — без рядка розміру і без «tokens freed»: обробник відповідає `skip`, і розмова справді не змінилась. Інваріант: у компактизації пакет непорожній, і кожна його правка або застосована, або в `failed`, тож тут `failed` непорожній.
- `applied` порожній, `kind = seed` ([SP_CTX_02_22](./context_editor.handoff.sp.md#SP_CTX_02_22)): `context-editor: no queued edit was applied. Not applied: <failed>.`, а коли `failed` теж порожній — порожній рядок. Рядка розміру немає: без правок розмір засіву відрізняється від видимих рядків лише прибраними службовими викликами мода, доданими CarryNote, головою-підсумком і нормалізацією (прибрані провідні рядки асистента й сирітські результати, рядок TRANSCRIPT_LINE), і «звільнено» про це було б неправдою.

NowIndex (фаза 18; живий прогін фази 15: звіт казав `rewrite #23`, а агент після DropOwnCalls бачив той самий рядок як `#18` і не міг зіставити звіт із переліком): у тексті звіту кожен опис з `applied`, для якого `produced` має запис (`produced.edit` = цей опис), отримує суфікс ` (now #<produced.index>)` — `rewrite #23 (now #18)`, `summarize toolu_X (now #12)`, `collapse #10..#14 (now #11)`, `describe #0 (now #0)`; описи без запису в `produced` (`drop`, правка, чийого рядка в кінцевому списку вже немає) лишаються як є. Індекс — рядок із текстом заміни (рядок результату пари для `summarize` і `collapse` з носієм, рядок підсумку для `collapse` без носія, переписаний рядок для `rewrite` і `describe`), у кінцевому списку, тобто в переліку `context_list` одразу після цього застосування (у засіві — у засіяній сесії). Одна форма для всіх видів: суфікс додається і коли індекс не змінився, а для `summarize` він важливий так само, бо пара отримала новий ідентифікатор (FreshId) і старий `tool_use_id` у переліку вже не знайти. Індекс чинний для переліку відразу після цього застосування; звіт, дописаний до ще не доставленого (RESUME_FAILED), несе індекси своїх застосувань, і пізніше застосування їх зсуває — прийнято, як і для будь-якого індексу з минулого переліку. Межі довжини звіту немає; суфікс додає ≤ 12 символів на правку (≤ MAX_QUEUE_EDITS правок), спливне повідомлення однаково обрізає звіт до 200 символів. Описи в `failed` суфікса не мають: їхні правки нічого не створили.

CommandNote ([SP_CTX_DEC_26](./context_editor.sp.md#SP_CTX_DEC_26), фаза 25): звіт застосування, що потрапляє в чергу (компактизація: застосовано, жодної правки, оригінали не заархівовано; звіт гілки збою FailedQueue), закінчується реченням COMMAND_NOTE ([SP_CTX_01_12](#SP_CTX_01_12)) — після всіх речень FormatReport і AttachText; спливне повідомлення людині (перші 200 символів звіту) іде без нього. Звіт засіву (`kind = seed`) його не має: рядки `/compact` засіву несуть HANDOFF_MARKER, який сам каже автора. Кілька недоставлених звітів, з'єднаних AppendReport, несуть речення кожен у черзі, але одне повідомлення доставляє його один раз: NoteOnce (`noteOnce` у `hooks/queue.ts`) лишає COMMAND_NOTE лише після останнього звіту, що його має (Flush — Resume і Optimize; DeliverReport); RemoveDelivered звіряє власний текст черги.

Порядок речень після базової форми (як у FormatReport): нотатки → DESCRIBE_DROPS → власні виклики → доставки. Після будь-якої з форм, коли `notesDropped` непорожній, додається ` Notes dropped (their rows were removed): <ids>.` Далі, коли серед `applied` є `describe`, — ` `+DESCRIBE_DROPS ([SP_CTX_01_12](#SP_CTX_01_12)). Далі, коли `ownCallsRemoved` > 0 і повернений список замінює розмову (у компактизації — `applied` непорожній; у засіві — завжди), додається OwnCallsText (`ownCallsText` у `hooks/edits.ts`): коли `applied` непорожній — ` Your context_* calls (<ownCallsRemoved>), including the ones that queued these replacements, were removed from the conversation; tags and notes stay — see context_list.` (лічильник — усі власні пари: `context_list`, `context_note`, `context_tag`, `context_edit`; заміни з тегу ставить у чергу `context_tag`, тож «made» було б неточно — рев'ю фази 28), інакше (засів без застосованої правки) — ` Your context_* calls (<ownCallsRemoved>) were removed from the conversation; tags and notes stay — see context_list.` (пропозиція P13: агент, чиї виклики `context_note` чи `context_edit` зникли з розмови, не впізнавав своїх дій — живі прогони фаз 14 і 17; з фази 28 речення прив'язує прибрані виклики до замін, які вони зробили, бо тексти замін називають власний виклик агента — [SP_CTX_DEC_17](./context_editor.sp.md#SP_CTX_DEC_17), A″; до фази 28 — ` Your own context-editor calls (<n>) were removed; tags and notes stay — see context_list.`). Далі, коли повернений список замінює розмову (у компактизації — `applied` непорожній; у засіві — завжди) і `deliveries.inserted + deliveries.removed` > 0, — ` Messages delivered during your tool calls: <inserted> now stand as rows, <removed> went with the rows your edits replaced.` (частина з нулем пропускається), а коли є `deliveries.unreadable` — ` Messages delivered during your tool calls could not be restored (<unreadable>).` (фаза 20: агент, який бачить на місці системного ходу рядок `user` з `<system-reminder>`, знає, звідки він; згорнуту доставку він бачив у попередженні постановки, [SP_CTX_02_02](./context_editor.edits.sp.md#SP_CTX_02_02)). Останнім, лише в компактизації з застосованою правкою, коли CommitAttachments ([SP_CTX_02_40](./context_editor.hostattach.sp.md#SP_CTX_02_40)) змінив відповіді і щось лишено поза запитом, — AttachText: ` Stale host attachments left out of each request from now on: <left.copies> older cop(y|ies) of instruction files and skill listings (<Estimate(left.chars, ratio)>).` (фаза 24; `left` — усе, що лишено поза запитом після цього застосування, не лише нове). Порожній звіт з однією з цих частин починається з `context-editor:`. `ratio` — `TagRegistry.charsPerToken`, прочитаний обробником (HandleCompaction уже читає реєстр) або BuildSeed; обробник телеметрії не запитує ([SP_CTX_02_34](./context_editor.stages.sp.md#SP_CTX_02_34)). Частини без даних пропускаються. Правило мінімальне: рядок розміру є тоді й лише тоді, коли застосовано хоч одну правку. `charsBefore` — розмір рядків, до яких правки застосовано (рядки події компактизації або видимі рядки засіву); `charsAfter` — розмір тих самих рядків після ApplyEdits і DropOwnCalls: у компактизації це повернений список, у засіві — до CarryNote і голови, тож «звільнено» рахує лише правки; рядки доставок, вставлені InsertDeliveries, у `charsAfter` не входять — у `charsBefore` їх теж не було (доставка не рядок).

### 01_06. Archive  {#SP_CTX_01_06}

- `<archives>` — каталог архівів сесії ([SP_CTX_01_07](#SP_CTX_01_07)). Файл `<archives>/<reportId>.json` — `ApplyReport.originals` одного застосування. У `result` викликів і результатів пари, чиї медіа заархівовано окремими файлами, кожен рядок у алфавіті base64 довжиною ≥ MEDIA_DATA у полі `base64` або `data` замінено на `[media archived: <шляхи>]`; інші рядки, зокрема довгий текст у цих полях, лишаються: дані медіа не дублюються в JSON. Шлях вписується в текст кожного зміненого рядка (`(original: <path>, open with Read)`, [C_CTX_DEC_18](./context_editor.core.concept.md#C_CTX_DEC_18)) лише тоді, коли файл записано.
- Медіа-файли: кожен замінений медіа-ресурс — файл `<archives>/<reportId>/<n>.<ext>` (`n` від 1 у межах застосування; `ext` за `mediaType`: `png`, `jpg`, `gif`, `webp`, `pdf`, інакше `bin`), записаний з декодованих даних. Шляхи вписуються в текст зміненого рядка (`(media: <path>, …)`); для `drop` — лише у звіт.
- Передача способом `transcript` пише за тією самою схемою для **старої** сесії: `<archives>/<id>.json` — оригінали змінених рядків, `<archives>/<id>/<n>.<ext>` — медіа замінених пар і медіа, перенесене файлами ([C_CTX_DEC_14](./context_editor.methods.concept.md#C_CTX_DEC_14)), `<storage>/<id>/seed.json` — засіяні рядки ([SP_CTX_01_17](#SP_CTX_01_17)); `id` — час збирання засіву, мс від епохи. Документ передачі, який після `/clear` не вдалося доставити, лишається копією `<storage>/<id>/document.txt` (`id` засіву, коли він є, інакше час збою; [SP_CTX_02_21](./context_editor.handoff.sp.md#SP_CTX_02_21)). Шляхи цих файлів вписано в текст засіяних рядків до очищення сесії, коли ідентифікатор нової сесії ще невідомий ([SP_CTX_DEC_09](./context_editor.sp.md#SP_CTX_DEC_09)).
- Зберігання: мод архіви не видаляє; їх обсяг обмежений сумою замінених і перенесених даних сесії. Винятки — файли засіву, який не дійшов до очищення сесії (відкладено або відмовлено): їх видаляє RunHandoff ([SP_CTX_02_21](./context_editor.handoff.sp.md#SP_CTX_02_21)), бо жоден рядок на них не посилається. Очищення — видаленням каталогу сховища і каталогу архівів ([SP_CTX_06_01](./context_editor.sp.md#SP_CTX_06_01)).

### 01_07. Storage  {#SP_CTX_01_07}

`<storage>` = `<HOME>/.claude/context-editor/<session_id>`. Без змінної `HOME`, з відносним `HOME` або з `session_id`, що не відповідає SESSION_ID ([SP_CTX_01_12](#SP_CTX_01_12)), сховище недоступне: шлях з такого id не будується (немає `..`, `/` і порожнього імені). Сховище прив'язане до поточного `session_id`: `/clear` і `/resume` у тому самому процесі змінюють сесію без події старту сесії, тому мод перед кожною операцією порівнює поточний `session_id` зі збереженим і за розбіжності готує сховище заново ([SP_CTX_02_15](./context_editor.tags.sp.md#SP_CTX_02_15)); черга і звіти попередньої сесії лишаються в її каталозі.

Опубліковане сховище екземпляра модуля — пара `session_id` і каталог (або `reason`): обидва змінюються разом, одним кроком наприкінці підготовки, і лише якщо її `session_id` досі поточний. До того лишається попередня пара: читач ніколи не бачить сховища без каталогу посеред підготовки і не бачить каталогу однієї сесії під id іншої. Для одного `session_id` водночас іде одна підготовка; другий виклик чекає її результату (AfterPrepare виконується один раз). Кожна операція (робота на послідовному ланцюжку, обробник інструмента чи події) бере каталог від EnsureStorage один раз — фонова робота події (AutoTag, RecordDelivery, R4, журнал) у момент події, а не коли настане її черга на ланцюжку — і всі свої читання й записи робить у ньому: робота, почата в сесії A, пише лише в каталог A, навіть якщо сесія тим часом змінилась. Порти мода отримують сховище в одній формі `{dir} | {reason}`; відмова кроку, якому потрібне сховище, — `storage unavailable: <reason>`.

| Field | Type | Description |
|-------|------|-------------|
| state | `ready` \| `unavailable` | `ready` — каталог існує і доступний лише власникові |
| reason | string? | Чому `unavailable` |

Архіви лежать не тут, а в каталозі архівів `<archives>` = `<cwd>/.claude/context-editor/<session_id>`, де `<cwd>` — робочий каталог сесії (`$.session.cwd()`), а `<session_id>` — ім'я каталогу сховища; каталог `.claude/context-editor/` (режим 700) несе власний `.gitignore` із `*`, який ArchiveRoot створює, коли його немає ([C_CTX_DEC_28](./context_editor.core.concept.md#C_CTX_DEC_28), фаза 35). Там: оригінали й медіа застосувань ([SP_CTX_01_06](#SP_CTX_01_06)), передачі й відновлення після resume, і `subagents/<agentId>/<tool_use_id>.txt` — повний вивід результату, обрізаного в розмові субагента ([SP_CTX_02_49](./context_editor.subagents.sp.md#SP_CTX_02_49), фаза 34). ArchiveRoot створює `.claude/context-editor/<session_id>` одним викликом (`umask 077`: каталог `.claude`, коли його ще не було, теж отримує режим 700). Без робочого каталогу, коли робочий каталог — `$HOME` (каталог архівів збігся б із `<storage>`, фаза 36), або коли каталог сесії не створюється, `<archives>` = `<storage>` для оригіналів і медіа основної розмови (як до фази 35), а результат субагента не обрізається. Засів передачі (`seed.json`), копія документа передачі і файли стану лишаються в `<storage>`.

Дані старих сесій ([SP_CTX_02_50](./context_editor.cleanup.sp.md#SP_CTX_02_50), фаза 36): `<storage>/archives.txt` — абсолютні шляхи каталогів архівів сесії, по одному в рядку (рядок на кожен робочий каталог), які ArchiveRoot дописує, коли вперше створює такий каталог; коли робочий каталог — `$HOME`, ArchiveRoot каталогу не дає (він збігся б зі сховищем); `<root>/<id>.zip` і `<archives>.zip` — запакована сесія, `<root>/<id>.where` — копія `archives.txt` поза `.zip`; `<root>/.sweep` — мітка останнього прибирання (час — її mtime), `<root>/.sweep.lock/` — замок прибиральника. Імена `<root>`, що не є SESSION_ID, SESSION_ID + `.zip` або `.where`, прибирання не чіпає.

Файли каталогу: `pending.json` (Queue), `tags.json` (TagRegistry), `aliases.json` (AliasRegistry), `boundary.json` (Boundary), `journal.json` (Journal, [SP_CTX_01_19](#SP_CTX_01_19)), `deliveries.json` (доставки хоста посеред ходу, [SP_CTX_01_22](#SP_CTX_01_22); фаза 20), `hostattach.json` (рішення про вкладення хоста, [SP_CTX_01_23](#SP_CTX_01_23); фаза 24), `ledger.json` (журнал входу застосувань, [SP_CTX_01_24](#SP_CTX_01_24); фаза 32), архіви й медіа-файли застосувань і передач ([SP_CTX_01_06](#SP_CTX_01_06)), перенесені вбік черги `pending.json.bad-<ms>`, файли доставок `deliveries.json.bad-<ms>` і файли рішень `hostattach.json.bad-<ms>`. Файли стану (`pending.json`, `tags.json`, `aliases.json`, `boundary.json`, `journal.json`, `deliveries.json`, `hostattach.json`) лежать у каталозі 700 і власних прав не потребують: `$.fs.write` прав не задає (новий файл — 644, навичка plugin-hooks, пункт 9), але інші користувачі до файлів у каталозі 700 не дістаються. Архіви й медіа-файли, як і раніше, пише команда хоста з `umask 077` (600). Запис кожного файлу стану командою хоста (пункт (d) фази 17) відкинуто: `tags.json` пишеться майже на кожен виклик інструменту, а процес на кожен запис — зайва затримка без виграшу в захисті. Файлу готовності немає: компактизацію запускає той самий модуль, що її обробляє ([C_CTX_DEC_09](./context_editor.core.concept.md#C_CTX_DEC_09)). Файл `editor-ready`, лишений версією з двома розширеннями, мод не читає і не пише.

**Порт сховища** (аудит PL_AUD_CTX, фаза 7, CF-15). Кожен JSON-файл стану (`pending.json`, `tags.json`, `aliases.json`, `journal.json`, `deliveries.json`, `hostattach.json`) читається і пишеться через один порт файлу з однаковою семантикою; модуль хуків прив'язує його до файлової системи хоста один раз.

- Читання дає один із трьох станів, як у Queue ([SP_CTX_01_04](#SP_CTX_01_04)): `missing` (файлу немає — значення за замовчуванням), `ok`, `unreadable` (не читається, не розбирається, не JSON-об'єкт або поле порушує обмеження свого розділу; причина — у `reason`). `unreadable` ніколи не трактується як порожнє значення. Збій самої перевірки існування файлу — помилка операції, а не `missing`.
- Читання-змінювання-запис іде на ланцюжку свого файлу ([SP_CTX_02](./context_editor.sp.md#SP_CTX_02)): прочитати, обчислити нове значення, записати. Зміна повертає нове значення або нічого (нічого не пишеться); результат — чи записано; збій запису відхиляє операцію. Нечитабельний файл обробляється одним із трьох способів, які називає виклик: лишити як є і зміни не викликати (типово), передати зміні сам стан `unreadable` (вона вирішує сама) або перенести файл убік (`<file>.bad-<ms>`) і змінювати значення за замовчуванням, як для `missing` (доставки, [SP_CTX_02_35](./context_editor.stages.sp.md#SP_CTX_02_35)). Якщо перенести не вдалося (немає прав, інша файлова система), зміна не викликається і нічого не пишеться: нечитабельний файл лишається на місці, а не перезаписується значенням за замовчуванням; для доставок цей запис втрачено.
- Порти модулів мають два контракти: **Update** — зміна бачить значення (`missing` — значення за замовчуванням), нечитабельний файл лишається як є; **Change** — зміна бачить стан читання, зокрема `unreadable`. В обох зміна, що повертає те саме значення, яке прочитано, нічого не пише: вміст файлу не змінився б, а відсутній файл і файл зі значенням за замовчуванням читаються однаково.
- Карантин нечитабельної черги (`context_edit`, [SP_CTX_02_02](./context_editor.edits.sp.md#SP_CTX_02_02)) і файлу доставок переносить файл у `<file>.bad-<ms>`; результат — новий шлях або нічого, якщо перенесення не вдалося. Без перенесення `context_edit` відмовляє (як і раніше), а RecordDelivery не пише.
- Перенесення реєстру в сховище нової сесії ([SP_CTX_02_21](./context_editor.handoff.sp.md#SP_CTX_02_21)) іде на ланцюжку реєстру: `missing` у старому сховищі нічого не пише; `unreadable` відхиляє крок з назвою реєстру («the tag registry of the old session cannot be read (<reason>)»).

- **Кеш реєстрів** (аудит PL_AUD_CTX, фаза 11, CF-22; конфлікт X1). Пам'ять екземпляра модуля для `tags.json` ([SP_CTX_01_10](#SP_CTX_01_10)), `aliases.json` ([SP_CTX_01_13](#SP_CTX_01_13)) і `hostattach.json` ([SP_CTX_01_23](#SP_CTX_01_23), фаза 24): читання файлу таким, яким цей екземпляр його востаннє прочитав або записав. Кеш лише для показу й воріт, які нічого не пишуть (перелік, звіт закриття, телеметрія, м'яке нагадування, вступ і порада з промптом людини, розв'язання `cN`, ворота NoteReminders); кожне читання-змінювання-запис (Update, Change і будь-яке читання на ланцюжку файлу для пізнішого запису — `context_tag`, `context_note`, AutoTag, R4, лічильник ходів, MarkAlias, NoteReminders, крок фіксації застосування, перенесення передачі) читає сам файл. Тож другий записувач тієї самої сесії (інший процес на `--resume`, старий екземпляр модуля після гарячого перезавантаження) не губить своїх змін: наступне читання-змінювання-запис бачить їх і оновлює кеш, а показ може відставати лише до нього. Ключ — (сесія, каталог, епоха): шлях файлу містить каталог сесії, а запис дійсний лише в поточній епосі кешу. Нову епоху (усі записи геть) починає кожна публікація сховища — старт сесії, `/clear`, `/resume` ([SP_CTX_02_15](./context_editor.tags.sp.md#SP_CTX_02_15)), — тож жодне читання не переходить в іншу сесію, зокрема й у сесію, до якої повернулися після того, як її міг писати інший процес. Читання файлу оновлює запис кешу; запис через порт замінює його записаним текстом (він розбирається при першому читанні); збій запису й карантин запис прибирають. Стан `unreadable` не кешується: наступне читання знову йде до файлу, і виправлений вручну файл видно одразу. Читання, що перетнулося із записом чи перенесенням того самого файлу (запис і перенесення рахуються зміною і на початку, і в кінці) або яке обігнала нова епоха, не лишає в кеші нічого, що пережило б кінець запису: воно могло побачити старий текст, а кінець запису замінює чи прибирає запис кешу. Перегляд дає закешоване читання без файлової системи й без ланцюжка файлу — для воріт у пам'яті (NoteReminders, [SP_CTX_02_33](./context_editor.stages.sp.md#SP_CTX_02_33)). Межа: файл, змінений повз порт (рукою, іншим процесом, старим екземпляром модуля), показ бачить з наступного читання файлу (читання-змінювання-запису) або з нової епохи; власні записи мод робить лише через порт. Черга, журнал і доставки не кешуються.

Правила R1–R3 не перезаписують наявний тег; R4 і R5 — лише в межах, названих у таблиці. Жодне правило не додає тегу до повного реєстру (межі TAGS_FULL [SP_CTX_02_11](./context_editor.tags.sp.md#SP_CTX_02_11)); з фази 30 повний реєстр видно агенту рядком телеметрії `Tags:` (RegistryFull, [SP_CTX_02_28](./context_editor.stages.sp.md#SP_CTX_02_28)), а не лише мовчанням правил. Результат-помилка пошукового інструмента — не вивід пошуку: R3 його не позначає (живий прогін фази 11 аудиту: `Grep` до інструмента, якого хост не має, отримав `review search`, CF-52); великий результат-помилка лишається для R2 — розмір займає контекст однаково. «Раніша пара» і «раніший рядок» — у поточній розмові ([SP_CTX_02_18](./context_editor.tags.sp.md#SP_CTX_02_18)) перед рядком, що спрацював; для R4 — пара `Read`, рядок виклику якої стоїть перед рядком виклику запису (паралельний `Read` у тій самій відповіді після запису не позначається; рядка виклику запису ще немає в розмові — ранішими вважаються всі). R5 (б) — умовний контракт. Головний випадок, заради якого він є, — повторно вкладений текст навички (P3: навичка dev-flow двічі по ~10 тисяч токенів); чи хост додає такий текст рядком поточної розмови і якими дверима, не перевірено, а вкладення хоста (перелік навичок, доставки `queued_command`) рядками `$.session.messages()` не є (навичка plugin-hooks, пункти 41 і 43). Тому фаза 15 починає з проби «Дублікат вставки навички» ([SP_CTX_05_03](./context_editor.scenarios.sp.md#SP_CTX_05_03)): якщо повторна вставка стоїть рядком поточної розмови, R5 (б) реалізується для дверей, які назве проба; якщо ні — R5 (б) цілком переходить у backlog плану з тригером повернення, а R5 (а) лишається. До фази 15 хук `session.append` мода слухає лише двері `prompt` і `tool-result` ([SP_CTX_02_12](./context_editor.tags.sp.md#SP_CTX_02_12)). Результат проби (фаза 15, 2026-10-10, stream-json, 2.1.295; `.dev_flow/cache/phase15/probe/log.jsonl`): текст навички, яку відкрив `Skill`, проходить `session.append` дверима `tool-message` (`origin { kind: tool, tool: Skill }`, `isMeta`), але рядком `$.session.messages()` (поточної розмови) не є, а повторний `Skill` тієї самої навички хост удруге не вставляє (рядок «Skill … is already loaded above», 73 символи). R5 (б) тому не реалізовано: він у backlog плану з тригером «хост почав передавати вставки навичок рядками розмови або агент скаржиться на дубльовану навичку»; R5 (а) реалізовано, хук і далі слухає лише `prompt` і `tool-result`.

### 01_13. AliasRegistry  {#SP_CTX_01_13}

Файл `<storage>/aliases.json`. Пише лише мод, на власному послідовному ланцюжку `aliases` (ранг 3: усередині `queue` і `tags`, ніколи навпаки, [SP_CTX_02](./context_editor.sp.md#SP_CTX_02)), через порт сховища ([SP_CTX_01_07](#SP_CTX_01_07)).

| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| next | int | yes | 1 | ≥ 1 | Номер наступного псевдоніма |
| last | — | — | — | — | Вилучено (фаза 21, [SP_CTX_DEC_20](./context_editor.sp.md#SP_CTX_DEC_20)): до фази 21 — останній виданий псевдонім, ціль `ref: "last"`. Файл зі старим полем читається, поле ігнорується і при наступному записі зникає |
| map | map<string, string> | yes | `{}` | ≤ MAX_ALIASES записів; ключ `c<число>`, значення — `tool_use_id` | Псевдонім → виклик |

Стани читання — як у Queue; `unreadable` (зокрема ключ не `c<число>`, число ключа ≥ `next`, порожнє значення, більше MAX_ALIASES записів) не трактується як порожній реєстр: позначок немає, жоден `ref` виду `c<число>` не розв'язується; `last` реєстру не читає і розв'язується й тоді ([SP_CTX_02_17](./context_editor.tags.sp.md#SP_CTX_02_17)). Новий псевдонім витісняє той, що на MAX_ALIASES номерів старший (`c<n − MAX_ALIASES>` для нового `c<n>`, без сортування; аудит PL_AUD_CTX, фаза 11): реєстр тримає лише псевдоніми з останніх MAX_ALIASES номерів, навіть коли частину з них прибрало застосування. Файл, що досі тримає більше за MAX_ALIASES (старіші номери, залишені до фази 11 поза прибраними), при першому переповненні втрачає всі номери нижче вікна. До фази 11 видалялися найстаріші (з найменшим числом), лише коли записів ставало більше за MAX_ALIASES. До фази 21 `last` брався з цього реєстру — останній *позначений* виклик; позначку отримують лише виклики від BIG_ROW і SEARCH_TOOLS ([SP_CTX_02_16](./context_editor.tags.sp.md#SP_CTX_02_16)), а реєстр живе в сховищі сесії (переживає `--resume` і переноситься передачею), тож після малого виклику `last` мовчки вказував на старіший, навіть з іншого процесу (живий прогін фази 20, s5).

### 01_14. Boundary  {#SP_CTX_01_14}

Файл `<storage>/boundary.json`: початок поточної розмови після останньої компактизації основної розмови. Пише лише мод ([SP_CTX_02_18](./context_editor.tags.sp.md#SP_CTX_02_18)).

| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| head | list<string> | yes | — | 1..HEAD_ROWS елементів | `fingerprint` перших рядків розмови, яку повернула компактизація |
| count | int | yes | — | ≥ len(head) | Скільки рядків повернула компактизація |
| host | string? | no | — | `hostId` на момент запису | Ідентичність процесу хоста, у якому межу записано; відсутня, коли `hostId` ще не прочитано або не вдалося прочитати |

Стани читання: файл відсутній або `unreadable` — межі немає, поточна розмова — увесь транскрипт. Поле `host`, що не є рядком, ігнорується: межа читається, але вважається записаною без `host`. Якій межі мод довіряє — [SP_CTX_02_18](./context_editor.tags.sp.md#SP_CTX_02_18), `Trusted`, і [SP_CTX_DEC_10](./context_editor.sp.md#SP_CTX_DEC_10).

Ідентичність процесу хоста (`hostId: string?`, пам'ять модуля) = `"<token>:<ppid>"`:
- `token` — значення змінної середовища HOST_ENV процесу хоста. Якщо змінної немає, модуль один раз ставить її `$.env.set` випадковим рядком (≥ 16 символів `[0-9a-z]`). Змінна живе в процесі хоста: переживає гаряче перезавантаження модуля, а новий процес (перезапуск, `--resume`) її не має (навичка plugin-hooks, пункт 32).
- `ppid` — вивід команди хоста `sh -c 'echo $PPID'`, тобто pid процесу `claude`. Дочірні процеси успадковують змінну середовища, тож прив'язка до pid відрізняє процес хоста, запущений з-під іншого.
- `ParseHostId(token, stdout)` — чиста функція: `stdout` після обрізання пробільних символів складається лише з десяткових цифр і `token` непорожній → `token + ":" + stdout`; інакше — відсутній.
- Читання — одне читання в польоті на екземпляр модуля (один виклик `$.env` і одна команда `echo`), яке модуль запускає в `session.start` або в першому PrepareStorage — що раніше; під час завантаження модуля `$` ще немає. Читання, що закінчилося ідентичністю, запам'ятовується на весь час життя екземпляра. Читання, що закінчилося без неї (збій виклику `$.env` чи команди, вивід не число), не запам'ятовується: наступний читач, що чекає, запускає нове, але не більше HOST_ID_READS читань на екземпляр. Читання, яке не закінчується, тримає своє місце: повтору тоді немає, читачі після тайм-ауту бачать `hostId` відсутнім, доки воно не закінчиться. Живий прогін фази 12 аудиту (`.dev_flow/cache/live-test/audit-p12-results.md`) показав, що хост завершує `$.process.run` приблизно через 30 с, тож на практиці читання закінчується (не підтверджено документацією хоста) ([SP_CTX_DEC_24](./context_editor.sp.md#SP_CTX_DEC_24)).
- Читачі поза компактизацією — CurrentRows, `Key()` і зняття `host` при перемиканні сесії в PrepareStorage — **чекають** читання, але не довше HOST_ID_WAIT_MS від його початку: вони працюють у шляхах інструментів, промптів і перемикання сесії, де бюджету ~1 с немає. Для них `hostId` відсутній, коли читання не вдалося або ще йде після HOST_ID_WAIT_MS. Тайм-аут не запам'ятовується: читання триває, і щойно воно дасть ідентичність, її бачать наступні читачі й обробники компактизації (`peek`); читачі, що прийшли після тайм-ауту, поки читання ще йде, не чекають ([SP_CTX_DEC_24](./context_editor.sp.md#SP_CTX_DEC_24)).
- Обробники компактизації (HandleCompaction, HandleSeed, спостерігач межі [SP_CTX_02_18](./context_editor.tags.sp.md#SP_CTX_02_18)) читання не чекають і, крім першого читання нижче, процесів не запускають: прочитано — значення, ще ні або не вдалося — `hostId` відсутній, і RecordBoundary пише межу без `host`. Якщо їхній PrepareStorage — перший, він лише запускає перше читання екземпляра, не чекаючи його (єдиний процес, який може запустити шлях обробника компактизації); повтору читання обробник не запускає ніколи (`kickHostId`). Обробник, що приєднується до підготовки, яку почав інший шлях і яка чекає читання, підганяє її: крок межі бере `hostId` лише якщо його вже прочитано ([SP_CTX_02_15](./context_editor.tags.sp.md#SP_CTX_02_15)).

Стан передачі в пам'яті модуля: `handoffInFlight: bool` (false) — RunHandoff цього екземпляра модуля йде (від першого кроку до повернення результату чи винятку; скидається на кожному виході); `handoffScheduled: bool` (false) — запуск RunHandoff уже заплановано через HANDOFF_DELAY і ще не почався; `requestTurn: int?` (відсутній) — значення `turns`, коли `context_handoff` поставив запит; перезавантаження модуля його губить, і тоді перерваний хід запиту не знімає; `instance: string` — мітка цього екземпляра для поля `owner`.

Invariants:
- Поки `handoffInFlight`, запит не належний за жодного віку: Schedule не планує нового запуску, захоплення його не бере, а `context_handoff` і `/handoff` відмовляють з DENIED_RUNNING — запит не можна замінити, хоч би скільки `/clear` чи компактизація засіву чекали кінця довгого ходу.
- RunHandoff не лишає запит у стані `running`, коли повертається або падає: кожен вихід — HandedOff, Fail, FailAfterClear або Defer ([SP_CTX_02_21](./context_editor.handoff.sp.md#SP_CTX_02_21)), хіба що не вдався сам запис старої черги цим кроком. Після засіву Seed перехоплює кожен збій на місці (обробник винятку RunHandoff його не бачить), а спливне повідомлення називає крок, що не вдався; коли не вдався HandedOff, воно каже, що стара сесія досі тримає запит `running`. Тож `running` без `handoffInFlight` буває лише тоді, коли процес перервано, модуль вивантажено посеред передачі або не вдався запис старої черги; через HANDOFF_STALE такий запит знову належний.

Функції над поточною розмовою `rows`:

    Distinctive(row) = row has a call, a result or a non-empty text            # рядок лише з thinking має відбиток "assistant||", який не розрізняє рядків
    MarkBefore(rows, i) = { anchor: fingerprint(rows[k]), hint: k } for the largest k < i with Distinctive(rows[k]); none → null
    MarkIndex(rows, m) = m null → -1; Locate(rows, m.anchor, m.hint) found → that index; else → lost   # Locate — SP_CTX_02_04
    StartOf(rows, after) = MarkIndex(rows, after) + 1, where lost counts as -1 (the block starts at the head)

Межа, рядок якої вже не знаходиться (`lost`: вбудована компактизація хоста, межа вийшла за вікно ROW_WINDOW), діє як голова для `after`; загублений `end` — кінець блоку невідомий, і його ніколи не показують як порожній блок (`null`). Перегляд, телеметрія і звіт закриття про це кажуть ([SP_CTX_02_01](./context_editor.edits.sp.md#SP_CTX_02_01), [SP_CTX_02_28](./context_editor.stages.sp.md#SP_CTX_02_28), [SP_CTX_02_29](./context_editor.stages.sp.md#SP_CTX_02_29)). context_tag і DetectOptimize, які читають поточну розмову, записують `null` на місце загубленого `stage.after` і `lastClosed.after` (для них `null` і `lost` означають те саме — голову); загублений `lastClosed.end` лишається як є, щоб не стати «порожнім блоком», а як `after` наступного блоку без етапу він діє як голова. Застосування правок і засів переносять межу за правилами [SP_CTX_02_14](./context_editor.tags.sp.md#SP_CTX_02_14).

Invariants:
- Відкриття етапу при відкритому етапі спершу закриває поточний ([SP_CTX_02_29](./context_editor.stages.sp.md#SP_CTX_02_29)); реєстр ніколи не має двох відкритих.
- `waiting` є лише при `lastClosed`; закриття чи відкриття етапу інструментом знімає `waiting` до того, як замінить `lastClosed` (звіт блоку, що чекав, — у результаті виклику), а мітка при `waiting` зливає блоки ([SP_CTX_02_30](./context_editor.stages.sp.md#SP_CTX_02_30)).
- `lastClosed` змінюють лише закриття етапу (інструментом або міткою) і мітка без відкритого етапу; RebindTags лише переносить його межі, а context_tag і DetectOptimize лише заміняють загублений `after` на `null`.

### 01_19. Journal  {#SP_CTX_01_19}

### 01_22. QueuedDelivery  {#SP_CTX_01_22}

Доставка хоста посеред ходу — вкладення `queued_command`: повідомлення людини, набране під час ходу, звіт субагента, сповіщення фонової задачі. Хост пише її записом-вкладенням транскрипту, що висить за рядком з `tool_result`, і показує моделі системним ходом; рядком розмови вона не є — її немає ні в `$.session.messages()`, ні в `e.messages` компактизації, ні в API-поданні. Рядок, повернений обробником компактизації з `handle`, хост копіює разом із вкладеннями за ним; перезібраний без `handle` — без них, і модель потім відрікається від власних слів про зниклий текст (спайк [context_editor_attachments](./context_editor_attachments.spike.md); навичка plugin-hooks, пункти 43–44). Мод записує текст доставки в мить появи ([SP_CTX_02_35](./context_editor.stages.sp.md#SP_CTX_02_35)) і вставляє його рядком, коли застосування чи засів повертає рядок, за яким вона висить, без `handle` ([SP_CTX_02_36](./context_editor.stages.sp.md#SP_CTX_02_36)). Фаза 20.

Файл `<storage>/deliveries.json` — `{ items: list<QueuedDelivery> }` у порядку запису, ≤ MAX_DELIVERIES записів і ≤ MAX_QUEUE_BYTES. Стани читання — як у черги: `missing` — порожньо, `unreadable` — файл не JSON, не об'єкт або запис не відповідає таблиці.

| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| uuid | string | yes | — | — | `uuid` події `session.append` доставки; для діагностики |
| anchor | list<string> | yes | — | 1+ ідентифікаторів | `tool_use_id` кожного результату рядка-якоря — останнього рядка основної розмови з дверима `tool-result`, що пройшов `session.append` перед доставкою |
| kind | `person` \| `agent` \| `task` \| `other` | yes | — | — | DeliveryKind(text), нижче |
| origin | string | yes | — | — | `origin.kind` події як є (`composer`, `unclassified`, `task-notification`, …); класу не визначає: людина в stream-json має `unclassified`, у терміналі — `composer` |
| text | string | yes | — | непорожній; обрізаний — голова і закривальні теги рамки разом не довші за MAX_DELIVERY_TEXT, плюс хвіст обрізання (розбір файлу допускає ще 100 символів хвоста) | відрендерений текст — текстові блоки `content` події, з'єднані `\n`, з рамкою `<system-reminder…>` як є; довгий — CutDelivery ([SP_CTX_02_35](./context_editor.stages.sp.md#SP_CTX_02_35)): рамка лишається цілою |

DeliveryKind(text): коли `text` без пробілів зліва починається з `<system-reminder`, береться перший непорожній рядок після рядка відкривного тегу; він дорівнює рядку DELIVERY_FRAMES — клас `person`, `agent` чи `task`; інакше (і без рамки) — `other`. Клас визначає текст, а не `origin`: походження розходяться між хостами, а звіти субагентів у VS Code мають у транскрипті `origin.kind: peer` (транскрипт decd4bc6: 3 `human`, 13 `peer`, 19 `task-notification`, усі за рядком з `tool_result`). `person` — повідомлення людини ([SP_CTX_02_02](./context_editor.edits.sp.md#SP_CTX_02_02), PersonText); `agent` і `task` — невідтворювані звіти, які агент може згорнути, як інші результати ([C_CTX_03_04](./context_editor.core.concept.md#C_CTX_03_04), «Відтворюваність»).

Invariants:
- Пара (`text`, спільний ідентифікатор в `anchor`) унікальна у файлі: копія доставки, яку stream-json після компактизації знову проводить через `session.append` (за копією рядка-якоря), нового запису не дає.
- Запис живе, доки рядок-якір лишається в розмові з `handle` (вкладення тоді переносить хост). Вставлений рядком, пішовши разом зі згорнутим чи прибраним якорем, або з якорем, якого вже немає в рядках компактизації (вбудована компактизація, межа), запис видаляється при наступному застосуванні мода ([SP_CTX_02_07](./context_editor.edits.sp.md#SP_CTX_02_07)).
- Файл належить сесії ([SP_CTX_01_07](#SP_CTX_01_07)); `--resume` у новому процесі має той самий `session_id`, тож записи лишаються. Передача файлу не переносить: засів несе доставки рядками ([SP_CTX_02_22](./context_editor.handoff.sp.md#SP_CTX_02_22)). Доставки форка сесії, старішої сесії чи такі, що прийшли до завантаження мода, записів не мають — запасне читання транскрипту (R2 спайку) — у backlog плану ([SP_CTX_DEC_19](./context_editor.sp.md#SP_CTX_DEC_19)).

| repeat | true? | no | — | Побайтовий повтор: перша копія серії лишається, решта пропускаються |
| drop | true? | no | — | Пропустити кожну копію (усі розділи застарілі й немає преамбули; перелік, усі назви якого має один новіший перелік) |
| stale | list<SectionKey>? | no | ≤ MAX_ATTACH_KEYS | Розділи, які копія замінює рядком SUPERSEDED |

TextHash(s) = довжина і два 32-бітні хеші (FNV-1a і djb2-xor) у base 36, через крапку; SectionKey(path, body) = TextHash(path + «\0» + trim(body)).

Invariants:
- Рішення змінюються лише в застосуванні мода, що змінило розмову, і в ClearAttachments; між ними хук відповідає за файлом, тож відновлений процес (`--resume`, пам'ять порожня) надсилає ті самі байти.
- Копія з преамбулою (PREAMBLE_HEAD) ніколи не пропускається цілком; вкладення, яке розбір не розуміє, і тип поза ATTACH_TYPES не мають рішення.
- Файл належить сесії; передача його не переносить (нова сесія має свої вкладення).

### 01_24. ApplyLedger  {#SP_CTX_01_24}

Журнал входу застосувань (фаза 32; спайк [context_editor_resume](./context_editor_resume.spike.md)): `handle` рядків, які застосування мода отримало на вхід і які після `--resume` хост може повернути оригіналами (оригінал до межі несе `handle`, що дорівнює його uuid, тобто `handle` рядка входу). Файл `<storage>/ledger.json`, ланцюжок `ledger` (ранг 4); пише HandleCompaction у фоні після точки фіксації (RecordInputs, [SP_CTX_02_44](./context_editor.resume.sp.md#SP_CTX_02_44)) і HandleRepair, що очищує його після ремонту ([SP_CTX_02_47](./context_editor.resume.sp.md#SP_CTX_02_47)); читають NeedsRepair, HandleRepair, HandleCompaction і BuildSeed (DropPulled, [SP_CTX_02_45](./context_editor.resume.sp.md#SP_CTX_02_45)). Стани читання — як у черги; `unreadable` запис переносить убік (карантин, [SP_CTX_01_07](#SP_CTX_01_07)) і починає новий журнал; читачі вважають його порожнім.

| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| clean | bool | no | — | лише `true` | Ремонт цієї сесії відповів «nothing to repair» після останнього застосування: NeedsRepair мовчить; RecordInputs і очищення після ремонту поле знімають (рев'ю фази 32) |
| entries | list<LedgerEntry> | yes | `[]` | Σ `handles` ≤ MAX_LEDGER_HANDLES; серіалізований файл ≤ MAX_QUEUE_BYTES — коли запис перевищив би межу, найстаріші записи видаляються, доки не вміститься | Записи від найстарішого |

LedgerEntry:

| Field | Type | Required | Constraints | Description |
|-------|------|----------|-------------|-------------|
| at | int | yes | мс від епохи | `reportId` застосування |
| handles | list<string> | yes | 1..MAX_LEDGER_HANDLES, без повторів (фаза 32, код: `e.messages` не має межі ROW_WINDOW) | `handle` рядків асистента і рядків з результатами входу застосування (промпти й інші рядки `user` без результатів не записуються — вони нічого не тягнуть) |

Invariants:
- Журнал належить сесії; передача його не переносить (засіяні рядки не мають `handle`).
- Після ремонту, що стоїть, журнал порожній: жоден рядок асистента чи результатів розмови не має `handle`, тож старі оригінали більше не підтягнуться.
- Журнал без запису не забороняє ремонту: залишкове правило DropPulled працює і без нього, якщо сесія мала застосування (запис `apply` журналу ефекту, [SP_CTX_01_19](#SP_CTX_01_19)).

### 01_25. Capabilities  {#SP_CTX_01_25}

Пам'ять модуля, з якої Capabilities ([SP_CTX_02_53](./context_editor.bypass.sp.md#SP_CTX_02_53)) виводить вердикти: один об'єкт на екземпляр модуля (процес хоста), без файлу; перемикання сесії його не скидає, перезавантаження модуля — скидає.

| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| attachments | int | yes | 0 | ≥ 0 | Скільки разів хост викликав хук `prompt.attachment` мода (будь-який тип) |
| mainTurns | int | yes | 0 | ≥ 0 | Завершені не перервані ходи основної розмови в цьому екземплярі |
| live | map<Capability, `reached` \| `passed`> | yes | `{}` | — | Живі ознаки цього процесу |
| probe | map<Capability, `reached` \| `passed`> | yes | `{}` | — | Результат зонда цього процесу |
| cache | map<Capability, `reached` \| `passed`> | yes | `{}` | — | Запис кешу для версії цього хоста ([SP_CTX_01_26](#SP_CTX_01_26)) |
| probeState | `none` \| `planned` \| `running` \| `done` | yes | `none` | — | Зонд цього процесу (один на процес) |
| version | string | no | — | `x.y.z` | `$.session.version().version`, прочитана один раз; відсутня — читання кинуло (кешу і зонда немає) |
| noticed | list<Capability> | yes | `[]` | — | Можливості, які PassedText уже назвав у цьому процесі |
| ownSeen | int | yes | 0 | ≥ 0 | Скільки власних міток мода (MARKER, HANDOFF_MARKER, REPAIR_MARKER) побачив обробник `session.compact` цього процесу; NoteCommandUnseen порівнює до і після команди |
| passSeen | int | yes | 0 | ≥ 0 | Скільки інших компактизацій основної розмови (не precompute) побачив обробник; маршрут `brief` пропускає ObservePassedCompact, коли лічильник зріс |

Capability: `compact` \| `attachments`.

Invariants:
- `attachments` і `mainTurns` лише зростають.
- Вердикт — функція полів (Verdict: `live` → `probe` → `cache` → `unknown`), окремо не зберігається.

### 01_26. CapabilityCache  {#SP_CTX_01_26}

Файл `<root>/capabilities.json` (корінь сховища `$HOME/.claude/context-editor/`, режим 700): вердикти за версією хоста, спільні для всіх сесій машини. Пише Merge ([SP_CTX_02_53](./context_editor.bypass.sp.md#SP_CTX_02_53)) записом цілого файлу (останній записувач виграє: записи різних процесів однієї версії однакові або новіші за живими ознаками); читає старт сесії. Нечитабельний — як порожній, наступний запис його замінює.

| Field | Type | Required | Default | Constraints | Description |
|-------|------|----------|---------|-------------|-------------|
| entries | map<string, CapEntry> | yes | `{}` | ≤ CAP_CACHE_VERSIONS ключів; при перевищенні видаляються записи з найстарішим `at` | Ключ — версія хоста |

CapEntry: `compact` і `attachments` — `reached` \| `passed` (кожне необов'язкове), `at` — мс від епохи, `source` — `probe` \| `live`.
