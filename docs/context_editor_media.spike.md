# Spike: Медіа в промптах людини і межі вікон трьох подань

> **Status:** concluded
> **Created:** 2026-10-10
> **Updated:** 2026-10-10
> **Author:** Claude (Opus 5.5) разом з alexandr.yavorsky
> **Time-box:** ~45 хвилин (витрачено ~25 хвилин живих прогонів і розбору)
> **Scope:** codebase (`register.ts` `apiMessages`, `edits.ts` `collectMedia`, типи хоста), prototype (одноразовий плагін `mprobe`, малі сесії `--model haiku` на закріпленому бінарнику 2.1.296: два прогони stream-json через fifo і два в терміналі в tmux)
> **Mode:** single
>
> **Target concept:** [C_CTX](./context_editor.concept.md)
> **Serves:** [SP_CTX_DEC_06](./context_editor.sp.md#SP_CTX_DEC_06), фаза плану [PL_CTX_P4](./context_editor.plan.md#PL_CTX_P4)
> **Question(s):**
> 1. Як зіставити повідомлення API-подання з медіа в промпті людини з рядком розмови: A — рівність тексту, B — позиція промптів людини в обох поданнях, C — відмова від `describe`?
> 2. Чи дорівнює текст такого повідомлення `Row.text` (точно, після якої нормалізації, як вкладено нагадування), і чи збігаються кількість і порядок промптів у поданнях, зокрема після компактизації?
> 3. Межі вікон трьох подань: `$.session.messages()`, `{ as: 'api' }`, `e.messages` обробника `session.compact` — скільки віддає кожне, обрізання на ROW_WINDOW, де кожне починається після компактизації.

## Context

`describe` замінює медіа в промпті людини описом. Рядок розмови (`SessionMessage`) медіа не має; його видно лише в API-поданні. `CollectMedia` ([SP_CTX_02_10](./context_editor.edits.sp.md#SP_CTX_02_10)) зіставляє медіа в результатах інструментів за `tool_use_id`, а для медіа в промптах `PromptMatch` поки завжди повертає «немає», тож `describe` відхиляється. Рішення DEC_06 чекало живих даних про нормалізацію API-подання.

## Exploration Log

### Entry 1 — 2026-10-10 — Проба і сценарії

**What was tried / researched:**
Плагін `mprobe` (`.dev_flow/cache/media-spike/probe/hooks/probe.ts`, function hooks як у мода): на кожному `turn.complete` основної розмови пише дамп — рядки `$.session.messages()` (роль, повний текст, виклики, результати, `handle`), API-подання так само, як його читає мод (`$.session.messages({ as: 'api' })`: блоки, текст повністю, для медіа — тип, довжина, хеш даних); у `session.compact` — те саме плюс `e.messages`. Промпт із міткою `[[probe:same]]` або `[[probe:flood]]` планує в `turn.complete` через `$.clock.after` команду `$.command.run({ command: 'compact', args: 'mprobe: <mode>' })`; обробник для `same` повертає `e.messages` як є (усі з `handle`), для `flood` — 4200 синтетичних рядків без `handle` перед ними (щоб дійти до ROW_WINDOW). Вбудована `/compact` (справжнє підсумовування) — промптом людини. Лог подій — `prompt.submit` і `session.append` (двері, походження, блоки). Хост 2.1.296 (`~/.local/share/claude/versions/2.1.296`), `--model haiku`, `--permission-mode bypassPermissions`; дочірній `claude` без успадкованих `CLAUDE*`.

Сценарії (PNG 24×24 суцільних кольорів, base64; кольори моделі називала правильно в усіх ходах):
- `run1` (stream-json, `drive.sh`): перший промпт сесії з зображенням (обвішаний нагадуваннями); лише зображення без тексту; текст–зображення–текст; два промпти з однаковим текстом і різними зображеннями; хід з `Read`; зображення після зміни файлу; `@notes.txt` у тексті; компактизація обробником `same`; вбудована `/compact`; `flood` до 4214 рядків після межі; ще одна `same` на цьому обсязі.
- `run2` (stream-json, `drive2.sh`): два зображення в одному промпті; текст з пробілами і `\n\n` на краях; лише зображення одразу після ходу з `Bash`; два однакові тексти; `same`; зображення після неї; той самий текст утретє.
- `term1`, `term2` (термінал у tmux, `term.sh`): зображення вставлено шляхом до файлу через bracketed paste (TUI робить з нього `[Image #N]`); лише зображення; два однакові тексти; `same`; зображення після неї; `@notes.txt` із зображенням; вбудована `/compact`; зображення після неї; `@blue.png` разом із вставленим зображенням.

**Findings:**
- **`Row.text` промпту** — його текстові блоки, з'єднані без розділювача: `[text "P3 part A.", image, text "P3 part B…"]` → `"P3 part A.P3 part B…"`; лише зображення → `""` у stream-json, `"[Image #2]"` у терміналі (TUI пише заповнювач у сам текст). Пробіли й `\n` на краях тексту людини зберігаються (`"  Q2 spaced text  \n\n"`). `prompt.submit` бачить той самий текст, з'єднаний через `\n`.
- **API-повідомлення промпту** — злиття: вкладення хоста (нагадування `<system-reminder>…` текстовими блоками — перед блоками промпту), сам рядок промпту з блоками в початковому порядку, далі isMeta-нотатка `[Image: source: <шлях>]` на кожне зображення. Нотатка — окремий рядок транскрипту (`session.append`: `door: note`, `isMeta: true`), якого немає в `$.session.messages()`; у stream-json хост зберігає вставлене зображення у `/tmp/claude-<uid>/<cwd-slug>/<sid>/images/<n>.png`, у терміналі — шлях вставленого файлу. Текст людини в API дослівний, але хост на стиках злитих повідомлень іноді додає `\n` у кінець текстового блоку (`"P1: …\n"`, `"…</command-args>\n"`), а перед медіа — ні.
- **Злиття рядків.** Підряд рядки `user` дають одне API-повідомлення: рядки команди `/compact <args>` і `<local-command-stdout>Compacted …` зливаються з наступним промптом, плюс хост додає блок `<local-command-caveat>…`, якого в рядках немає. Два промпти stream-json, надіслані один за одним, поки сесія була зайнята (щойно після компактизації від плагіна), стали одним промптом (`prompt.submit` — тексти через `\n`) і одним рядком (тексти через `""`).
- **Повідомлення без рядка.** У терміналі `@notes.txt` дає окреме API-повідомлення `user` лише з `<system-reminder>Called the Read tool…` (не злите з сусіднім), а результат читання — нагадуванням у повідомленні промпту. `@blue.png` кладе зображення файлу першим блоком у повідомлення промпту, поряд із вставленим зображенням. У stream-json `@notes.txt` у тексті нічого не вкладає.
- **Після компактизації обробником** (`same`): `$.session.messages()` — оригінали, далі копії, далі рядки команди; API-подання починається з першої копії; копії рядків з медіа несуть і медіа, і нотатки `[Image: source]` (хост переносить вкладення разом із рядком з `handle`, пункт 44 навички).
- **Після вбудованої `/compact`:** рядок `user` з підсумком («This session is being continued…»), копія останньої відповіді асистента, рядки команди; API починається з підсумку. У терміналі рядок підсумку стоїть одразу після останнього рядка промпту до межі — в рядках це один суцільний відрізок `user`.
- **Термінал під час компактизації:** і `$.session.messages()`, і API-подання закінчуються рядком промпту `/compact <args>` (поза ланцюжком, пункт 24 навички), якого немає в `e.messages`; у stream-json його немає ніде.

### Entry 2 — 2026-10-10 — Перевірка A і B на даних

**What was tried / researched:**
`match.py` (офлайн, `.dev_flow/cache/media-spike/match.py`) проганяє кандидати на всіх 51 дампі (`runs/*/dump-*.json` плюс варіанти з `e.messages` замість рядків) і на трьох штучно зіпсованих (вилучено рядок промпту з лише зображенням, вилучено рядок одного з двох однакових промптів, вилучено API-повідомлення). Результати — `.dev_flow/cache/media-spike/runs/v2.txt`, `runs/match-all.txt`.

**Findings:**
- **A (рівність тексту) сама по собі не працює.** Промпт лише із зображенням має `""` у stream-json — рівний кожному іншому такому промпту; однакові тексти дають до 5 кандидатів (оригінали, копії й повтор після компактизації: `a10 → [12, 14, 31, 33, 42]`); проста нормалізація (зняти один `\n` у кінці блоку) ламає промпт з `\n\n` на кінці. Рівність без пробільних символів після вилучення блоків-прикрас стабільна на всіх даних, але лише як перевірка, не як ключ.
- **B «k-й промпт від початку» не працює:** кількість не збігається (`prompt rows 16, prompt msgs 9` у `run2`) — рядки містять оригінали до межі, рядки команд зливаються з промптом, у терміналі є API-повідомлення без рядка.
- **B від хвоста з перевіркою кожної пари (B+A) працює.** Обидва подання закінчуються тим самим ходом; одиниця — відрізок рядків `user` разом із рядками асистента після нього проти API-повідомлення `user` (крім повідомлень лише з прикрас) разом з повідомленнями асистента після нього. На всіх 51 дампі (обидва хости, до і після обох видів компактизації, у вікні 4096, з `e.messages` у трьох компактизаціях) кожне повідомлення з медіа в промпті отримало правильний рядок (перевірено за хешем зображення і відповіддю моделі), без жодного «немає». Єдина зупинка — на першому повідомленні API-подання після вбудованої `/compact` у терміналі (підсумок у рядках злитий з рядком до межі), вона нічого не зачепила.
- **Зіпсовані дані:** перевірка лише тексту промпту пропускає зсув (промпт лише із зображенням `""` «вміщується» в будь-що, і один з двох однакових промптів віддав своє зображення сусідові); з рівністю в обидва боки і перевіркою тексту асистента всі три зсуви виявлено, хибних зіставлень немає (повідомлення на межі зсуву — «uncommitted»).

### Entry 3 — 2026-10-10 — Межі вікон

**What was tried / researched:**
`flood` повернув 4200 синтетичних рядків + 14 справжніх; далі ще один хід і компактизація `same` на цьому обсязі (`run1`, дампи 18–21).

**Findings:**
- `$.session.messages()` — рівно 4096 найновіших рядків усього транскрипту, з рядками до межі (у `t13` починається з `flood u 118`).
- `{ as: 'api' }` — рівно 4096 найновіших повідомлень від останньої межі, перше — `user` (`flood u 112`): повідомлення зливають рядки (thinking і текст однієї відповіді, відрізки `user`), тож за однакового ліміту API-вікно сягає далі в історію, ніж вікно рядків. Після компактизації обробником воно починається з першого поверненого рядка, після вбудованої — з підсумку.
- `e.messages` — **усі** рядки після останньої межі, без ліміту 4096 (4214 у `dump-19`), кожен з `handle`; у терміналі без рядка `/compact <args>`, який є в обох інших поданнях.
- Отже, рядки CurrentRows — суфікс `e.messages` (за вікна — коротший на `len(e.messages) − 4096`), а API-вікно від межі — теж суфікс; хвости всіх трьох подань збігаються (з поправкою на рядок `/compact` у терміналі).

### Entry 4 — 2026-10-10 — Під час виклику інструмента і паралельні виклики

**What was tried / researched:**
Після рішення розробника (B+A) перед реалізацією — проба в мить `tool.call` (`context_edit` читає обидва подання посеред ходу): хук `tool.call` для `Bash` у `mprobe`, `run3` (`drive3.sh`): промпт із зображенням; два послідовні `Bash` в одному ході; два паралельні `Bash` в одній відповіді.

**Findings:**
- Посеред ходу обидва подання вже мають рядок поточного виклику (`tool_use` без результату) — хвости збігаються.
- Паралельні виклики: рядки — «виклик, результат, виклик» (пункт 40 навички), а API — одне повідомлення асистента з двома `tool_use` і одне повідомлення `user` з результатами. Одиниця «відрізок рядків `user`» (Entry 2) тут розходиться (перевірка по `calls`), тож одиницею став хід людини: від рядка з промптом до наступного промпту (крок 3 нижче). На всіх 66 дампах і варіантах (`runs/v3.txt`, `match_v3` у `match.py`) результат той самий, що й раніше, плюс правильні зіставлення в `run3`; три зіпсовані дампи так само дають «немає».

## Conclusion

**Verdict:** concluded — рекомендовано B+A (розробник обрав B+A 2026-10-10: [SP_CTX_DEC_06](./context_editor.sp.md#SP_CTX_DEC_06), реалізація — фаза 5): позиційне зіставлення від хвоста з перевіркою текстом (варіант B, де A — перевірка кожної пари, а не ключ). Точне правило для `PromptMatch` у SP_CTX_02_10:

1. **Хвіст.** Якщо останнє API-повідомлення — `user`, останній рядок — асистента, а текст повідомлення без прикрас і без пробільних символів починається з `/compact`, це повідомлення відкинути (термінал під час компактизації).
2. **Прикраси.** Текстовий блок API — прикраса, якщо після пробілів на початку починається з `<system-reminder>`, `<local-command-caveat>` або `[Image: source: ` (PROMPT_DECORATIONS). Рядок — прикраса за тим самим правилом і тими самими трьома початками (вставлені модом доставки чи такі рядки хоста); прикраси не входять у порівняння тексту й не можуть бути власником. API-повідомлення `user`, у якому лише блоки-прикраси, — без рядка.
3. **Одиниці (ходи).** У рядках одиниця починається з рядка `user` без `toolResults`, текст якого не прикраса, якщо попередня одиниця вже має рядок асистента (або одиниці ще немає); до неї входять усі рядки до наступного початку, а її «голова» — рядки `user`, що стоять підряд від початку до першого рядка асистента. В API одиниця починається з повідомлення `user`, у якому є текстовий блок, що не прикраса, або медіа, за тієї самої умови; повідомлення лише з прикрас нічого не починає. Рядки до першого початку (і повідомлення до першого початку) не входять у жодну одиницю.
4. **Пари від хвоста.** k-та одиниця з кінця рядків ↔ k-та з кінця API, k = 1, 2, …, доки є обидві. Пара перевірена, якщо: `squash(тексти рядків user одиниці, крім прикрас, по порядку) == squash(текстові блоки повідомлень user одиниці, крім прикрас)`; мультимножини `tool_use_id` результатів рівні; `squash(тексти рядків асистента) == squash(текстові блоки повідомлень асистента)` (thinking не входить); мультимножини `tool_use_id` викликів рівні. `squash` вилучає всі пробільні символи (`\s`). Перша неперевірена пара зупиняє вирівнювання.
5. **Довіра.** Пара k довірена, якщо пари 1..k перевірені і пара k+1 перевірена, або її немає, або вона не перевірилась на першому повідомленні API-подання (підсумок чи початок вікна).
6. **Власник.** Для довіреної пари, перше повідомлення якої має блоки `image`/`document` верхнього рівня: власник — єдиний рядок голови одиниці без `toolResults`, текст якого не починається з `<command-name>`, `<local-command-stdout>` чи прикраси; якщо в цьому повідомленні є `tool_result` або таких рядків не один — «немає»; медіа в інших повідомленнях одиниці (доставка посеред ходу) — «немає». Власнику належать усі медіа-блоки верхнього рівня повідомлення (зокрема зображення файлу з `@шлях` — воно зникне разом із перезібраним рядком, пункт 44 навички).
7. Інакше «немає» (`unmatchedPromptMedia` += 1).

Правило однакове для `rows` = CurrentRows (`context_edit`, `context_list`) і `rows` = `e.messages` (застосування в `session.compact`), бо хвости подань збігаються.

**Key constraints discovered:**
- `Row.text` = текстові блоки, з'єднані `""`; `prompt.submit` — через `\n`; API — дослівні блоки, з можливим `\n` на стиках злиття. Порівнювати лише без пробільних символів.
- API-повідомлення = злиття суміжних рядків `user` + вкладення + isMeta-нотатки; повідомлення лише з вкладень буває окремим (термінал, `@файл`).
- Вікна: рядки — 4096 найновіших з усього транскрипту; API — 4096 найновіших повідомлень від межі; `e.messages` — усе від межі, без ліміту.
- Термінал під час компактизації: зайвий хвостовий рядок `/compact <args>` у двох поданнях з трьох.
