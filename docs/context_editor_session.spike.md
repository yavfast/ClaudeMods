# Spike: Нова сесія з очищеним контекстом через новий файл транскрипту (схема B)

> **Status:** concluded
> **Created:** 2026-10-09
> **Updated:** 2026-10-15
> **Author:** Claude (Opus 5.5) разом з alexandr.yavorsky
> **Time-box:** 1 сесія
> **Scope:** codebase (типи хоста, локальні транскрипти `~/.claude/projects/`), prototype (скрипти й тестові сесії в scratchpad, живі запуски в tmux)
> **Mode:** single
>
> **Target concept:** [C_CTX](./context_editor.concept.md)
> **Serves:** [C_CTX_DEC_11](./context_editor.methods.concept.md#C_CTX_DEC_11), опосередковано [C_CTX_DEC_05](./context_editor.core.concept.md#C_CTX_DEC_05)
> **Question(s):**
> 1. Чи відкриває `claude --resume <id>` транскрипт, зібраний поза хостом з очищених рядків (підсумки замість результатів, згорнуті діапазони, переписані висновки), і чи бачить модель саме очищений контекст — з парами викликів інструментів?
> 2. Чи можна переключитися на нову сесію автоматично в тому самому процесі (`$.command.run({ command: 'resume', args: id })`), і що при цьому відбувається з плагінами та сховищем редактора?
> 3. Які поля записів JSONL обов'язкові, що можна опустити, і наскільки формат стабільний між версіями хоста (2.1.294 → 2.1.295)?

## Context

Правки редактора застосовуються компактизацією від обробника, а `claude --resume` її не поважає: відновлена сесія бачить оригінали ([C_CTX_DEC_05](./context_editor.core.concept.md#C_CTX_DEC_05)). Розробник запитав про команду на зразок `/compact`, що створює нову сесію з очищеним і м'яко стисненим контекстом і дає на неї переключитися. Розглянуто три схеми ([C_CTX_DEC_11](./context_editor.methods.concept.md#C_CTX_DEC_11)): A — передача документом через `/clear`; B — новий файл транскрипту; C — `--fork-session` з правками в копії (не працює). Схема B зберігає структуру розмови і закрила б DEC_05, але спирається на внутрішній формат транскрипту хоста, тож потребує перевірки на хості перед рішенням.

## Exploration Log

### Entry 1 — 2026-10-09 — Відновлення зібраного транскрипту (Q1)

**What was tried / researched:**
Справжня сесія з трьох ходів (`claude -p`, хост 2.1.295) у тестовому каталозі: Read `big.txt`, Read `noise.txt`, текстовий хід. Скрипт `assemble.py` зібрав з її JSONL новий файл `<новий uuid>.jsonl` у тому самому каталозі проєкту: свіжі `uuid` усіх рядків, ланцюжок `parentUuid` перев'язаний повз видалені рядки, новий `sessionId`; результат `big.txt` замінено підсумком лише з KEY_0042, пару `noise.txt` (виклик, результат і їхні вкладення) видалено, один висновок переписано. Відновлення — `claude -p --resume <новий id>` без інструментів і інтерактивно в tmux.

**Findings:**
- Модель бачить саме очищений контекст: KEY_0042 знає «з підсумку, що замінив вміст big.txt», KEY_0377 — UNKNOWN, бачить один виклик Read (`big.txt`) з підсумком замість результату, `noise.txt` «не читала», переписаний висновок цитує. Повторено окремим запуском головного агента (`--fork-session`) — той самий результат.
- Модель читає лише `message.content`; поле `toolUseResult` (там лишався оригінал з KEY_0377) — тільки для інтерфейсу.
- Контекст: ~36k токенів проти 69.8k в оригіналі на тому самому ході (`/context`: повідомлення 9.5k).
- Далі сесія звичайна: новий хід дописується в той самий файл з нормальним ланцюжком; повторний `--resume` знову показує очищений вміст; інтерактивний `--resume` показує очищену історію. Підписані thinking-блоки після зміненого раннього контексту API приймає.
- Модель помічає неузгодженість переписаного висновку з рештою розмови («не довіряй цьому») — підсумки й переписи мають бути самоузгодженими.

### Entry 2 — 2026-10-09 — Перемикання в тому самому процесі (Q2)

**What was tried / researched:**
Одноразовий плагін: інструмент ставить запит на перемикання, після `turn.complete` і паузи 300 мс плагін викликає `$.command.run({ command: 'resume', args: id })`; окремо — `command: 'clear'`.

**Findings:**
- Працює: `session.end` з `reason = resume`, `$.session.id()` одразу повертає новий id, інтерфейс перемальовується з очищеною історією, наступний хід її бачить, інструменти плагінів лишаються. `clear` теж працює (`reason = clear`).
- `session.start` при цьому не приходить (ні для resume, ні для clear); `classic.SessionStart` у хуках модів не спрацював навіть при старті. Причину перемикання видно лише з `session.end.reason`.
- Невдалий resume (невідомий id) не відхиляється: `command.run` резолвиться `{}`, у транскрипті рядок «Session … was not found». Успіх перевіряється порівнянням `$.session.id()` до і після.
- Виклик із хука, якого чекає хід, відхиляється: «command.run: called from a tool.call hook, it would wait on the turn this hook is holding; run it from a later event (turn.complete)».
- Сховище редактора саме переходить на нову сесію (`ensureStorage` створює `~/.claude/context-editor/<новий id>/`); старий каталог лишається.
- Рядок стану показує заповнення контексту з `message.usage`, скопійованого зі старого ходу, доки не пройде новий хід.

### Entry 3 — 2026-10-09 — Обов'язкові поля і стабільність формату (Q3)

**What was tried / researched:**
Варіанти зібраного файлу з прибраними полями, кожен перевірено відновленим ходом; порівняння назв ключів рядків у 131 транскрипті версій 2.1.286–2.1.295 (лише назви ключів).

**Findings:**
- Мінімальна схема, яку приймає `--resume`: лише рядки `type` `user`/`assistant` з полями `type`, `uuid`, `parentUuid` (у першого — `null`), `timestamp` (ISO), `message: { role, content }`.
- Без `timestamp` — явна відмова «No conversation found with session ID». Без `uuid` чи `parentUuid` — **тиха** відмова: сесія відкривається, але модель майже нічого не бачить. Сирітський `tool_result` (без свого `tool_use`) хост мовчки прибирає.
- Без наслідків прибираються: `sessionId`, `cwd`, `version`, `gitBranch`, ідентифікатори запиту й моделі, `toolUseResult`, `message.usage`, вкладення, системні рядки, рядки заголовка, черги, знімків файлів тощо.
- Рядки, розбиті по блоках одного повідомлення, мають спільний `message.id` — його треба зберігати або зливати блоки.
- У рядках `user`/`assistant` версій 2.1.286–2.1.295 поля `uuid`, `parentUuid`, `timestamp`, `message` є завжди; нове в 2.1.295 — лише `assistant.requestedModel`. Типи вкладень і службових рядків між версіями змінюються сильно — їх варто не переносити.
- Вбудований `/compact` пише рядок `system` `compact_boundary` і рядок `user` з `isCompactSummary`.

## Alternatives Considered

| # | Approach | Pros | Cons | Verdict |
|---|----------|------|------|---------|
| A | Передача документом через `/clear` | лише задокументований API; `/clear` через `$.command.run` перевірено | контекст — одне повідомлення, без пар викликів і медіа; правки редактора однаково не переживають `--resume` старої сесії | viable (простіший, слабший) |
| B | Новий файл транскрипту з очищених рядків | модель бачить очищену розмову з парами викликів; переживає `--resume`; автоматичне перемикання працює; контекст удвічі менший у тесті | недокументований формат; помилки ланцюжка тихі; немає API для каталогу транскриптів | viable with constraints |
| C | `--fork-session` + правки в копії | — | відновлення повертає оригінали | rejected |

## Conclusion

**Verdict:** схема B здійсненна з обмеженнями (хост 2.1.295): `claude --resume` відкриває зібраний поза хостом транскрипт, модель бачить саме очищену розмову з парами викликів, а плагін може переключитися на неї сам через `$.command.run({ command: 'resume', args: id })` після `turn.complete`. Вибір між A і B — за розробником ([C_CTX_DEC_11](./context_editor.methods.concept.md#C_CTX_DEC_11)).

**Key constraints discovered:**
- Формат транскрипту внутрішній; обов'язкові поля рядка — `type`, `uuid`, `parentUuid`, `timestamp`, `message`; помилка в ланцюжку `uuid`/`parentUuid` не дає помилки, а порожній контекст.
- API для шляху до транскриптів немає: файл сесії шукається як `<id>.jsonl` у `~/.claude/projects/*/` (з урахуванням `CLAUDE_CONFIG_DIR`).
- `$.command.run` не можна викликати з хука, якого чекає хід; невдалий resume не відхиляється — успіх перевіряється за `$.session.id()`.
- Перемикання не дає `session.start`; редактор уже переживає це через `ensureStorage`.

**Recommendations for the concept:**
- Писати лише рядки `user`/`assistant`: свіжі `uuid`, строгий ланцюжок `parentUuid`, скопійований `timestamp`, новий `sessionId`, `message` з `role`, `content` і `id`; без `message.usage` і без `toolUseResult` (там лишаються оригінали); пари викликів цілими; свій рядок заголовка; файл 0600 через тимчасовий файл і перейменування.
- Перевіряти зібраний файл перед перемиканням: ланцюжок від останнього рядка до першого покриває всі рядки, кожен `tool_result` має свій `tool_use`.
- Підсумки й переписи мають бути самоузгодженими з рештою розмови.
- Модульні тести збирача на зразках транскриптів кількох версій; живий сценарій «нова сесія» після кожного оновлення хоста.
- Схема B робить DEC_05 неактуальним для сесій, створених так.
