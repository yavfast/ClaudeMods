## 05. Verification Criteria — інваріанти, інтеграційні сценарії

### 05_02. Invariant Checks  {#SP_CTX_05_02}

| Invariant | Verification method |
|-----------|-------------------|
| Пари виклик—результат цілі | після ApplyEdits кожен id виклику має результат і навпаки (модульні тести); наживо — API не відхиляє запит |
| Справжнє підсумовування не запускається через мод | журнал налагодження після команди мода з MARKER або HANDOFF_MARKER: `a hook's N messages stand … core never ran` або `skip`; у неінтерактивному хості — `result` «Not compacted · <reason>» або засіяні/змінені рядки, ніколи підсумок; модульний тест: кожна гілка HandleCompaction і HandleSeed, зокрема збій, відповідає списком або `skip`; Flush і Seed не запускають команду, коли від планування почався хід (`MovedSince`). Гарантія не абсолютна. Залишкове вікно: хід, що почнеться за мілісекунди між перевіркою `MovedSince` і постановкою команди в чергу хоста, з вивантаженням модуля або невдалим гарячим перезавантаженням під час цього ходу, лишає в черзі хоста `/compact <MARKER>` без обробника — хост виконає справжнє підсумовування ([C_CTX_DEC_09](./context_editor.core.concept.md#C_CTX_DEC_09)) |
| Рядки команди несуть самопояснювальну мітку, і обробник бачить її ж | після застосування і після засіву транскрипт і API-подання містять рядок команди `/compact` з MARKER або HANDOFF_MARKER дослівно (з фази 25 обидві кажуть, що команду запустив мод, а не людина); журнал обробника — `instructions` дорівнює тому самому тексту (спайк context_editor_handoff_long, Entry 4, «Мітка в рядках команди») |
| Засіяна сесія переживає відновлення | `claude -p --resume <new>` новим процесом: модель бачить засіяні рядки, а не порожню розмову; перед межею у файлі сесії лише рядки `/clear` |
| Змінені тексти позначено | починаються з MARK |
| Файли мода доступні лише власникові | права каталогу `<HOME>/.claude/context-editor` і каталогу сесії — 700; архівів і медіа — 600; файли стану лежать у каталозі 700 і власного режиму не потребують |
| Не більше одного відкритого етапу і одного тегу `state` | модульні тести context_tag і DetectOptimize: після кожного запиту в реєстрі ≤ 1 `stage`, ≤ 1 тег `state` |
| `optimize` і `optimizePrompted` не обидва `true` | модульні тести Flush, DetectOptimize і DeliverReport: жоден запис черги не лишає обидва; заміна — порівнянням-і-записом |
| Межі етапів — розрізняльні рядки | після CloseStage, DetectOptimize, RebindTags і засіву кожна межа — `null` або відбиток рядка з ідентифікатором чи непорожнім текстом (Distinctive) |
| М'яке нагадування нічого не запускає і не дублюється | модульні тести SoftHint, TurnSuggestion і DeliverReport: жоден шлях не пише черги, не відкриває і не закриває етапу; на один виклик — не більше одного рядка псевдоніма і одного рядка пропозиції (з фази 23 — окремі рядки; нагадування нотаток `[context-editor] reminder …` — окремі рядки, [SP_CTX_02_33](./context_editor.stages.sp.md#SP_CTX_02_33)); на один промпт — не більше однієї пропозиції; стан `hint` — порівнянням-і-записом |
| Префікс до першої зміни незмінний (фаза 23, лише з `keep_cache`) | модульні тести ApplyEdits і HandleCompaction з `freeze` / `keepCache`; без них префікса немає (`prefix` = 0): рядки `[0..prefix)` — ті самі рядки входу з `handle`, власні пари в них лишаються, доставки за ними не вставляються; наживо — `firstdiff.py` проксі-журналу: перша відмінність запиту після застосування — не раніше відповіді першої правки ([SP_CTX_DEC_22](./context_editor.decisions-21.sp.md#SP_CTX_DEC_22)) |
| Чужі записи черги не гублять `optimize` і `optimizePrompted` | модульні тести HandleCompaction (усі гілки), context_edit, QueueTagReplacements, RemoveDelivered |
| Основна розмова не обрізається (фаза 34) | модульні тести ShapeSubagentResult: без `agentId` рядок без змін і без запису архіву |
| Вкладення хоста змінюються лише застосуванням і не губляться | модульні тести AttachmentAnswer, PlanAttachments, CommitAttachments, ClearAttachments: рішення пише лише застосування, що змінило розмову, і ClearAttachments; копія з преамбулою цілком не пропускається; невідоме вкладення і `*_delta` лишаються; наживо — сценарій «Застарілі копії інструкцій після застосувань» |

### 05_03. Integration Scenarios  {#SP_CTX_05_03}

Живі сценарії в окремому екземплярі Claude Code з розширенням (`--plugin-dir mods/context-editor --debug`) у двох хостах: інтерактивний термінал під керуванням tmux (драйвер `.dev_flow/cache/live-test/ce.sh`) і неінтерактивний хост з потоковим входом у режимі stream-json, яким його запускає розширення VS Code (`-p --input-format stream-json --output-format stream-json`; драйвер `.dev_flow/cache/handoff-long/drive.sh`). Разовий `claude -p "<prompt>"` поза межами ([SP_CTX_05_04](./context_editor.edges.sp.md#SP_CTX_05_04)). Статус `pass (2026-10-08, після раунду 3)` — повторний прогін на коді після виправлень рев'ю раундів 1–3; просто `pass` — лише на прототипі до виправлень. Статуси pass до 2026-10-09 отримано на двох розширеннях (коміт b090f48), у терміналі; після переходу на одне розширення і компактизацію командою сценарії «Стиснення в межах сесії», «Три операції», «Скриншот у результаті інструменту», «Незмінене медіа», «Перегляд після компактизації», «Автоматичне чищення з тегів», «Захист початкового завдання» і всі сценарії передачі проганяються заново в обох хостах; доти їхній статус — історичний. Сценарій «Нагадування з початку» вилучено 2026-10-10 разом з Nudge ([SP_CTX_02_09](./context_editor.edits.sp.md#SP_CTX_02_09)); його місце займають сценарії етапів, мітки оптимізації й авторозмітки зі статусом `pending (задача етапів)`. Події ходу від команд мода не очікуються (спайк context_editor_handoff_long, Entry 4); сценарії лише фіксують їхню відсутність у журналі. Хост — Claude Code ≥ 2.1.295.
