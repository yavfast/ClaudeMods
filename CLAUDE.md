# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Mods for Claude Code: plugins built from **function hooks** (TypeScript modules listed in `hooks/hooks.json`, run by the host, not shell hooks from `settings.json`). Work follows the dev-flow process: concept → spec → plan in `docs/`, then code in `mods/`, with per-task state in `.dev_flow/`. Docs, README and `.dev_flow/` are written in Ukrainian. Code, code comments and commit messages are in English.

## Commands

```sh
# run Claude Code with the mod loaded
claude --plugin-dir ~/Projects/ClaudeMods/mods/context-editor

claude plugin validate mods/context-editor          # module validator (also checks how `$` is passed around)
claude plugin test mods/context-editor              # runs every tests/*.test.ts of the mod
sh mods/context-editor/tests/skill-limits.sh        # SKILL.md: description ≤ 250, file ≤ 9000 chars (tests have no fs)

# type check (there is no global tsc)
npx -p typescript@5.6.3 tsc -p mods/context-editor/tsconfig.json --noEmit
```

`claude plugin test` takes only a directory and has no filter. To run one test file, point it at a temporary folder that holds just that file plus the `hooks/` it imports.

`mods/*/tsconfig.json` extends `.claude-plugin/types/tsconfig.json`. Claude Code generates that folder each time it loads the mod, and git ignores it. In a fresh clone, the types and `tsc` only work after the mod has been loaded once with `--plugin-dir`.

## Architecture

### One plugin that both runs and handles the compaction

`mods/context-editor` gives the agent the MCP tools `context_list`, `context_edit`, `context_tag`, `context_note` and `context_handoff`, the skill `context-editor:context-stages`, and the person the command `/handoff`. The first prompt of a session carries the skill's whole text as hidden context (GUIDE_FRAME + SKILL.md read from `$.plugin.root`; INTRO_TEXT if unread), and after another compaction that stands the next prompt carries the short INTRO_TEXT (`reintroduce`, SP_CTX_DEC_36); subagents get neither, as the mod refuses their `context_*` calls; instead a subagent's big tool result (≥ SUB_CUT_AT chars of text, not `Read`, not the mod's own tools, no media) is cut at `session.append` to a head, a cut line naming its archive and a tail; the archive goes to the archive folder, `<cwd>/.claude/context-editor/<session_id>/subagents/<agentId>/<tool_use_id>.txt` (that folder holds its own `.gitignore` of `*`; without it the result is not cut; SP_CTX_02_49, `hooks/subagents.ts`). The agent decides when to optimize: it closes a task stage with `context_tag`, or ends an answer with the `[context-editor: optimize]` line, which starts an optimization turn. Nothing reminds it to clean: a separate soft hint line, `[context-editor: suggestion]` (after a big output once the conversation is large and has grown, or with the person's next prompt after a run of them), only proposes compressing the outputs not compressed yet, with the gain, the prompt-cache cost and a break-even verdict; `context_list` shows context telemetry on request, including where the API's ~20-position cache lookback starts. Edits are not applied right away. They go into a queue file. After a turn of the main conversation, Flush runs the built-in `/compact` with the marker `context-editor: apply queued edits (run automatically by the mod …, not by the person)` (MARKER: the host frames the command's rows as the person's, so the args say who ran it) through `$.command.run`, and the mod's own `session.compact` handler, matching on that `instructions` text (or the marker before phase 25, `markerKind`), applies the queue and returns the new rows; only when the agent asked for it (`keep_cache` in `context_edit`) do the rows before the response that holds the first change come back as they came, with their `handle` (the frozen prefix: the prompt cache holds up to it). Any assistant row returned with its `handle` (the prefix or an untouched response) pulls its original back by `message.id` after `--resume`; the first new host process repairs the conversation once (`hooks/repair.ts`: REPAIR_MARKER, planned from `session.start` through `$.clock.after`). Then Flush logs one line for the person (`$.ui.log`: edits applied and tokens freed; the model never sees it) and sends the resume prompt; an apply report carries COMMAND_NOTE (that `/compact` row is the mod's, not the person's), once per delivered message.

The person's own plain `/compact` (a `command.run` hook on `compact`, any origin but `plugin`, empty args) runs no host compaction: the hook answers with a line for the person, writes a `compact` optimization request into the queue and plans Flush (unless planned), which applies what is queued and then sends one prompt, so the agent compresses the conversation itself; `/compact host` runs the host's summary, other args and every plugin's run pass unchanged (the host skips the hook for the mod's own `$.command.run` as `re-entry`; its `.catch` lets it through). DetectOptimize ends the compression turn and toasts when it queued nothing.

A plugin's `$.command.run({ command: 'compact', args })` reaches that plugin's own hooks, works in the non-interactive host too, and arrives with `trigger: 'manual'`. `$.session.compact` is never used: the host skips the calling plugin's own hooks for it, and the non-interactive host refuses it outright. That is why the mod no longer needs a second plugin or a ready file.

The handoff (`context_handoff`, `/handoff`) builds a seed from what the model sees, runs `/clear`, then `/compact` with `context-editor: seed the handed-off conversation`; the handler returns the seeded rows in place of the cleared session's. Media of untouched pairs goes as files named in the result text.

Commands run only from a deferred action (`$.clock.after`) planned in `turn.complete`, in `session.start` (the repair) or in the `/handoff` command handler, never from a timer made in a `tool.call` or `prompt.submit` hook. Each command gets one attempt; the host's refusal text goes into the reasons or the status line.

Shared state lives on disk at `$HOME/.claude/context-editor/<session_id>/`, a directory with mode 700. It holds `pending.json` (the queue), `tags.json`, `aliases.json`, `boundary.json`, `journal.json` (the journal of effect), `deliveries.json` (the host's mid-turn deliveries, recorded so an apply can put them back as rows), `hostattach.json` (the answers to the host's stale copies of instruction files and skill listings, so a resumed process sends the same bytes), `ledger.json` (the handles of each apply's input rows, ApplyLedger: what a resume may put back), and the handoff's seed files. The archives of the replaced originals with their media (applies, handoff, repair) go to the archive folder `<cwd>/.claude/context-editor/<session_id>/` (ArchiveRoot, `archivesOf` in `register.ts`; it falls back to the storage folder when the project has none), because the host refuses a Read outside the project without the person's permission (C_CTX_DEC_28).

### Ports pattern (how the code is split for testing)

Faking the whole host `$` is expensive, so the logic sits in pure modules behind small IO interfaces, and `register.ts` binds those interfaces to `$`:

- `hooks/rows.ts`: the rows kernel (pure, L0, imports no other hook module): row predicates (`isPromptRow`, the one prompt predicate; `isPromptRowStrict`, ResolveLast's variant; `isEmptyRow`, `isPlainUserRow`), `resultsOf`, the pair lookup `findToolUse`/`findToolResult`, sizes (`rowChars`, `totalChars`, `charsOf`), `squash`/`sameText`, `apiBlocks`, `errorText`, the worth-editing policy (`isBig`, `isSearchTool`, `worthEditing`), the mod's text prefixes: `MARK` (the mod's own service lines; before phase 28 also every replacement), `PREFIX` with `modText()` (every mod text PersonText must skip is built from them), the replacement texts (`REPLACED` = `Later, your context_`; `SUMMARIZED`, `REWRITTEN`, `DESCRIBED`, `collapsedWords` name the agent's `context_edit` call, the `TAG_*` openers a `disposable` tag's replacement, `QueuedEdit.via = 'tag'`: agent-first, no MARK, SP_CTX_DEC_17 A″) with their predicates `isReplacementText` (a full opener of `REPLACEMENT_OPENERS` or MARK: old sessions keep their texts), `isCollapseText`, `isDescribedText`, and the compaction markers `MARKER`, `HANDOFF_MARKER` with `markerKind`. A shared row predicate or literal goes here, not into a copy (rule STRUCT-01).
- `hooks/edits.ts`: edit, listing and media logic (pure, incl. the frozen prefix and the one response-start algorithm: Responses, ResponseStart over `isPromptRow` of `rows.ts`), and the compaction boundary: CurrentRows (`ViewIO`), the host process identity and which boundary to trust. Also the per-event `Snapshot` (CurrentRows, Key() and the API form read at most once per event or tool call; `register.ts` passes one snapshot to every port of the call) and `RowIndex` (`indexRows`: Locate and the pair lookup for a pass over many targets).
- `hooks/media.ts`: PromptMatch, which ties media in a person's prompt in the API form to its row (pure; used by CollectMedia in `edits.ts`).
- `hooks/queue.ts` (`QueueIO`): the queue, `context_edit`, and delivering the report.
- `hooks/compaction.ts` (`CompactionIO`, `ObserveIO`, `FailureIO`): the markers, which branch a compaction takes, applying queued edits inside `session.compact`, the handler's failure branch (`compactionFailed`), and the observer of another compaction (`observeCompaction`: Copied, the boundary, the tags of rows it left out and `lastApply` dropped in one registry change, `pruneDeadTags`).
- `hooks/flush.ts` (`FlushIO`, `TurnEndIO`): the order of the end of a turn (`afterTurn`: DetectOptimize → turn count → Flush, the handoff besides), running the compaction command after a turn (or after the person's `/compact`, `requestFlush`), with a calibration before it when edits are queued (`calibrate` port, bounded by CALIB_WAIT_MS through `sleep`), the person's line of the apply (`logApplied`, `$.ui.log`, never seen by the model; SP_CTX_02_43) and the resume or optimization prompt.
- `hooks/personcompact.ts` (`PersonCompactIO`): the person's `/compact` (`compactRoute` by origin and args, `requestCompact` in the queue, `personCompact`, `compactFailure` for the hook's `.catch`).
- `hooks/turns.ts`: the turn counter Flush, AutoTag and the handoff share.
- `hooks/store.ts` (`PrepareIO`, `FileIO`): the storage of the current session: its one readiness form `{dir} | {reason}`, PrepareStorage (one run per session id, the session id and folder published together, SESSION_ID check) and EnsureStorage; every operation keeps the folder it got. Also the storage port: `Read<T>` (missing / ok / unreadable), `jsonFile` (a `Store<T>` per JSON state file: read, write, quarantine, `update(change, { onUnreadable, skipUnchanged, within })` on the file's chain), the port contracts `Update<T>` / `Change<T>` (`updateOf`, `changeOf`), `carry`, the parse helpers (`jsonObject`, `bytes`, `isCount`, `trimOldest`), and `serialChains`: one chain per file kind, ranked queue → tags → aliases → deliveries | journal | hostattach | ledger; a nested chain of a lower or equal rank goes to the debug log. And `FileCache`: the tag and alias registries and `hostattach.json` as this module instance last read or wrote them, keyed by path (the session's folder) and epoch; every storage publication (`prepareStorage`, a session switch) starts a new epoch, a Store write replaces its entry; it serves only views and gates (`Store.cached`, `Store.peek`), while `Store.read` and every read-modify-write read the file, so a second writer is never overwritten from a stale entry. Port names follow the contract: `update*` is Update, `change*` is Change.
- `hooks/repair.ts` (`RepairIO`, `NeedsIO`, `RepairHandlerIO`): the repair after a resume (phase 32): ApplyLedger (`ledger.json`) with RecordInputs, DropPulled (the originals a resume put back beside their copies, by the handles the ledger names, plus a residual rule by ids), NeedsRepair (`repeatsIn`: `$.session.messages()` carries no handles), ScheduleRepair and RunRepair (one attempt per session; after a switch in the process from the turn end), HandleRepair (REPAIR_MARKER: originals with a twin go, assistant and result rows come back without `handle`, prompts keep it).
- `hooks/handoff.ts` (`HandoffIO`, `SeedIO`): the handoff request, BuildSeed, CheckSeed, CheckSeeded, RunHandoff, HandleSeed and `parseSeedNames`.
- `hooks/tags.ts` (`TagIO`, `AppendIO`), `hooks/aliases.ts` (`AliasIO`): tags, auto-tagging rules and the `session.append` body (`appendRow`), `context_tag` (incl. stage open/close), the pins of an edit (`pinsFrom`), dead tags after another compaction (`pruneDeadTags`) and a full registry (`registryFull`), and the `cN` call aliases (a number given out and gone since: `aliasGone`).
- `hooks/stages.ts` (`ListIO`, `BlockIO`, `DetectIO`): `context_list` (`contextList`, with `listLabels`/`listAliases`; only a page with rows renews the listed key), stages and their row marks, the close report, the optimization mark and turn texts, telemetry (`measure` of one usage read) and calibrated size estimates (`calibrateBeforeApply` for Flush, `CalibrateIO`).
- `hooks/hints.ts` (`HintIO`): the soft hint: its two channels (a marked output, the person's next prompt), its candidates, proposal and text, and its state (`hint` in `tags.json`).
- `hooks/cache.ts`: what an apply costs the prompt cache (CacheShape: API positions over Responses of `edits.ts`, computed once per estimate; the lookback start; the rewrite from ResponseStart, the start FrozenPrefix uses), the break-even and the verdict (pure).
- `hooks/notes.ts`: the agent's service notes (`context_note`), their relocation after edits, and note reminders.
- `hooks/journal.ts` (`JournalIO`): the journal of effect: what each application compressed, own writes of compressed paths, rereads of compressed content and archives.
- `hooks/deliveries.ts` (`DeliveryIO`): the host's mid-turn deliveries (`queued_command`: the person's messages typed during a turn, subagent reports, task notifications): RecordDelivery from `session.append`, InsertDeliveries after a rebuilt anchor row in the compaction and the seed, and PersonText with the frames it reads (`queue.ts` re-exports it; `edits.ts` reads it for CollapsedList).
- `hooks/hostattach.ts` (`AttachIO`, `AttachApplyIO`, `AttachPort`): the host's attachments that are no rows (`instructions`, `nested_memory`, `skill_listing`): ParseAttachment (sections by `Contents of <path> (…):`), the `prompt.attachment` answer (AttachmentAnswer: keep, rewrite stale sections to a `superseded` line, or leave out), the catalog of asks since the last pass (AttachMemory), and the decisions made only inside the mod's apply (PlanAttachments: a newer copy of the path, or the file on disk differs from a comparable newest copy; FrozenAttachments for `keep_cache`; CommitAttachments on the `hostattach` chain inside the commit), saved in `hostattach.json`; ClearAttachments after another compaction that stands (answers void until the next apply). A listing goes only when one newer listing names all its skills (later listings are incremental). VerifyPredictions at the first turn end after an apply withdraws a prediction the host did not fulfil and calls `$.ui.invalidate('prompt.attachment')`, the only call of it (the host asks every attachment again after a compaction anyway). Subagents, `*_delta` and unknown framing are always kept.
- `hooks/subagents.ts` (`ShapeIO`): ShapeSubagentResult, the cut of a subagent's big tool result at `session.append` before AppendRow (`cutText`, `shapeSubagentResult`; SUB_* constants).
- `hooks/tools.ts`: the static metadata of the tools and the `/handoff` command: names, descriptions and JSON schemas (`TOOLS`, `HANDOFF_COMMAND`); the limits they name are interpolated from the constants that enforce them.
- `hooks/register.ts`: binding only: the event hooks, the module instance's memory, and the ports bound to `$`: `files($)` binds `FileIO` to `$.fs` once, `stores($, dir)` gives the seven stores of a session's storage, each on its `serialChains()` chain (`chainOf($, key)` for work whose folder arrives later). Every read-modify-write goes through a Store on its chain; where a port takes a change function, it is the Update/Change contract (`updateOf`/`changeOf`). Some pure modules still read and write a Store by hand inside `onChain` (backlog CF-44).

Tests in `tests/*.test.ts` use `claude-code/testing`, call these pure functions with fake IO objects, and build `SessionMessage` rows by hand. New logic belongs in a ports module with a test. `register.ts` should only do the binding.

### Traceability IDs

Code comments and commit subjects cite IDs from `docs/`: `C_CTX_*` (concept), `SP_CTX_NN_MM` (spec sections, e.g. `[SP_CTX_02_06]`), `PL_CTX_P*` (plan phases), and `*_DEC_*` (design decisions). Commit subjects start with the doc codes they touch, e.g. `[PL_CTX][SP_CTX][C_CTX] ...`. When behavior changes, update the spec section that the comment cites. The concept and the spec are split sets: the umbrella (`docs/context_editor.concept.md`, `docs/context_editor.sp.md`) lists its child files (`context_editor.mechanisms.concept.md`; `context_editor.<module>.sp.md`, e.g. `edits`, `tags`, `handoff`, `stages`), and `docs/_index.md` maps each ID prefix to its file; find a section by its anchor (`grep -rl '{#SP_CTX_02_06}' docs/`). `docs/context_editor.structures.sp.md` §01_12 holds the full constants table.

## Host behavior you must know

`.dev_flow/skills/claude-code/plugin-hooks.md` lists host pitfalls found by testing live, against Claude Code 2.1.294–2.1.296 (older hosts are not supported). Read it before changing hooks. The ones you hit most often:

- A hook has the shape `($, e, next)`. If it never calls `next`, it answers the event itself. Modules have no Node or DOM APIs, so everything goes through `$`. The validator allows `$` to be passed only to functions declared at the top level of the same file. A `tool.call` matcher must be a string or regex literal (no template strings: `${...}` in a matcher gives `tool=?`). One module may register an event without a matcher only once (e.g. one `session.compact` hook). `$.env.get` and `$.env.set` take the variable's name only as a string literal (the validator lists the names), so `'CONTEXT_EDITOR_HOST'` is spelled out at each call.
- Hooks that can refuse (`tool.call`, `prompt.submit`, `session.compact`) need `.catch`. Without one, a failing hook is skipped and the event goes on. `.catch` has a budget of about 1 s. In `session.compact`, the `.catch` must return `{ skip }` for the mod's own instructions, so that a failure never falls through to a real summarizing compaction.
- Never await `$.prompt.submit` inside a `session.compact` hook: it deadlocks. A refused prompt resolves with `{ drop }`. It does not throw.
- `$.command.run` queues a command until the session is idle and returns after the work (`compact` once the handler answered, `clear` once `$.session.id()` is new). Its refusal is final. It refuses a call from a timer made inside a `tool.call` hook. The mod's own `/clear` and `/compact` raise no `prompt.submit`, `turn.start` or `turn.complete`.
- The non-interactive host (VS Code, SDK, stream-json) has no `/resume` for `$.command.run`, and `$.session.compact` always fails there; `clear` and `compact` work. In a one-shot `claude -p "<prompt>"`, every `$.command.*` after the last turn fails with "no session is bound in this process".
- In stream-json every row a compaction handler returns passes through `session.append` again, with an origin that depends on the row: prompt rows `origin.kind = 'plugin'`, assistant rows `model '<synthetic>'`, tool-result rows `origin.kind = 'tool'` (so an origin filter does not catch copied results; the mod remembers their `tool_use_id`s until the next turn). In the terminal those rows and the command's rows bypass `session.append`.
- A row without `handle`, or with a `handle` from another session, loses its media and thinking blocks.
- A compaction runs only between turns; a command started mid-turn waits for the turn's end, and a turn may start meanwhile, so recheck the turn counter after each command. `/clear` and `/resume` change `session_id` without a `session.start`, so check the session before each storage operation. The read of the conversation is "originals + copies" only in the host process that ran the compaction; after `--resume` or `/resume` it is the loaded chain. So `boundary.json` is trusted by host process: it carries `host` = `<CONTEXT_EDITOR_HOST token>:<ppid>` (one read in flight per module instance; readers wait at most HOST_ID_WAIT_MS from its start, a timeout is not memoized and a read without the identity is retried up to HOST_ID_READS times; compaction handlers only peek and start at most the first read, never a retry, SP_CTX_DEC_24), or this module instance wrote it in this session; a session switch in the same process strips `host` from the new session's boundary (SP_CTX_DEC_10).
- `$.fs.read` and `$.fs.write` are capped at 4 MiB. Write larger files through `$.process.run(['sh','-c','umask 077 && cat > "$1"','sh',path], { stdin })`.

## Live testing

Unit tests don't cover how the host behaves. Run live scenarios in a separate `claude --plugin-dir mods/context-editor --debug` process: in the terminal inside tmux, driven by a script, and in the non-interactive host in stream-json mode (`-p --input-format stream-json --output-format stream-json`), as VS Code runs it. The debug log goes to `~/.claude/debug/<session>.txt`. The current task's drivers are `.dev_flow/cache/live-test/ce.sh` (terminal) and `.dev_flow/cache/handoff-long/drive.sh` (stream-json); git ignores `.dev_flow/cache/`. To find the active task and its next step, read `.dev_flow/active_context.md`.
