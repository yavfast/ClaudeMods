# Моди Claude Code: базові API плагіна: модуль, `$.fs`, `$.process`, `$.tool`, `.catch`, ідентичність процесу, перезавантаження, підключення

Тематичний файл навички [ClaudeCodePluginHooks](plugin-hooks.md): пункти 9, 11, 12, 14, 28, 31, 32, 34, 39, 42, 45, 56, 58, 68 її списку пасток, дослівно і з тими самими номерами (якір `#p<N>`), тож посилання «plugin-hooks N» / «навичка, пункт N» ведуть сюди через [покажчик](plugin-hooks.md#pitfalls). Посилання «пункт N» у тексті — на номер у тому самому списку, хоч би в якому тематичному файлі він лежав.

## Applicability Boundary

- **when_to_use:** пишете або змінюєте мод у `mods/` і зачіпаєте цю тему (базові api плагіна).
- **when_not:** класичні хуки `settings.json` (команди оболонки) — інший механізм.
- **version_or_context_scope:** версії хоста, на яких перевірено кожен пункт, — у [вхідному файлі](plugin-hooks.md#applicability-boundary); `state: stale` — на встановленому хості 2.1.299 і хості VS Code 2.1.301 пункти не перезвірено (рішення про перезвірку наживо — за розробником).

## Pitfalls

<a id="p9"></a>
9. **`$.fs.write` і `$.fs.read` мають межу 4 MiB**; великі файли пишіть через `$.process.run(['sh','-c','umask 077 && cat > "$1"','sh',path], { stdin })`. `$.fs` не задає права доступу — `chmod` через `$.process.run`.

<a id="p11"></a>
11. **`$.tool.list()`** показує інструменти поточного процесу — так один плагін перевіряє, що інший завантажений саме тут.

<a id="p12"></a>
12. **`.catch` має бюджет ~1 с**: не чекайте в ньому довгих ланцюжків — відповідайте одразу, решту робіть у фоні.

<a id="p14"></a>
14. **`$.tool.register` обрізає `description` до 2048 символів** і пише про це в TUI; важливе ставте на початок опису.

<a id="p28"></a>
28. **`$.model.fork` дає форкнутому агенту інструменти**: він може їх викликати (кожен виклик відхиляється), і відповідь забруднюється — у промпті форку прямо забороняйте виклики. Перевірено на 2.1.295.

<a id="p31"></a>
31. **Гаряче перезавантаження модуля — лише в терміналі й лише за зміни вмісту файлу** (`touch` не досить); у stream-json зміна файлу нічого не робить, доки не надіслати повідомленням `/reload-plugins` (новий екземпляр модуля, середовище процесу те саме). Перезавантажений модуль пише в транскрипт «<plugin>: reloaded (N hooks…)» і втрачає весь стан у пам'яті — і таймери (пункт 29), і прапорці на зразок довіри до власних файлів. Після `--resume` у stream-json журнал налагодження називається за тимчасовим id сесії; процес, відновлений з тим самим id, пише в той самий `~/.claude/debug/<sid>.txt`, що й інший процес цієї сесії. Перевірено на 2.1.295.

<a id="p32"></a>
32. **Ідентичність процесу хоста** для мода: токен, записаний `$.env.set` (успадковують дочірні процеси — прив'язуйте до pid), плюс `$PPID` з `$.process.run(['sh','-c','echo $PPID'])`; обидва не змінюються при гарячому перезавантаженні модуля і нові після перезапуску/`--resume`. `ps -o lstart= -p $PPID` теж дає час старту, але `ps` є не скрізь (slim-контейнери, busybox). `$.session.usage().startedAt` і `$.session.id()` після `--resume` не змінюються. `$.env.get`/`set` приймають лише рядковий літерал (валідатор сканує назви). Перевірено на 2.1.295.

<a id="p34"></a>
34. **Один модуль хуків на плагін** (2.1.295): друге `modules` у `hooks/hooks.json` валідатор відхиляє.

<a id="p39"></a>
39. **Плагін з function hooks може мати власні навички** (2.1.295, проба `claude -p` 2026-10-10): тека `skills/<name>/SKILL.md` поруч із `hooks/`; валідатор її приймає, агент бачить навичку в переліку як `<plugin>:<name>` з описом із frontmatter; повний текст — лише коли агент її відкриє.

<a id="p42"></a>
42. **Живі прогони: закріплюйте версію хоста.** CLI оновився з 2.1.295 до 2.1.296 посеред прогону; бінарник конкретної версії — `~/.local/share/claude/versions/<version>`.

<a id="p45"></a>
45. **Хуки `classic.*` у модулі можуть не отримати подію**: вбудований `cc-plugin-sec-default` відповідає на `classic.SessionStart` (і, судячи з усього, на `Stop`, `PreCompact`, `PostToolUse`) сам, у журналі «<plugin>: classic.SessionStart bypassed by cc-plugin-sec-default (tier user)». `transcript_path` звідти не взяти; шлях до транскрипту — `$HOME/.claude/projects/<$.session.cwd() з не-буквено-цифровими → '-'>/<$.session.id()>.jsonl` (пункт 17), читати через `$.process.run` (файл буває > 4 MiB). Перевірено на 2.1.295.

<a id="p56"></a>
56. **Підключити мод до вже запущеної сесії** (2.1.296, VS Code, сесія d5614704). `--plugin-dir` діє лише на старті процесу. Без перезапуску: (а) локальний маркетплейс — тека з `.claude-plugin/marketplace.json`, `source` плагіна лише відносний `./…` (абсолютний шлях валідатор відкидає, символьне посилання не читає), потім `claude plugin install <mod> --marketplace <тека> -s local` (вмикає в `.claude/settings.local.json` проєкту, маркетплейс записується в користувацькі налаштування) і `/reload-plugins` повідомленням у сесії — інструменти мода з'являються в тому самому ході; установка бере знімок файлів, тож зміни в `mods/` до сесії не доходять, доки знімок не оновлено. Оновлення знімка (2026-10-12): плагін локального маркетплейсу хост читає просто з його теки (`claude plugin list --json` → `readFromFolder`), тож досить `rsync -a --delete --exclude .claude-plugin/types --exclude tests mods/<mod>/ <маркетплейс>/plugins/<mod>/` і `/reload-plugins`; `claude plugin update` відповідає «nothing to update … Edits there take effect at the next session start or /reload-plugins», версія в `plugin.json` не потрібна; (б) `~/.claude/dev-mods/<session_id>/` — тека модів, які пише сам Claude (документація code.claude.com/docs/en/plugins/mods/create.md): за згодою на гаряче перезавантаження («Enable for this session», діє і після відновлення сесії) моди з неї завантажуються в кінці ходу і перезавантажуються після ходу, що їх змінив; без згоди — на наступному старті сесії; `/reload-plugins` нових тек не додає. У сесіях bd80217a, 8e44a3be і a3902d56 там лежало символьне посилання на `mods/<mod>` (іде за репо); чи підхопить хост вручну створене посилання в сесії без такої згоди — не документовано й не перевірено. Конфлікт імен: копія з `--plugin-dir` мовчки заміщує встановлену з маркетплейсу (у журналі `--debug` — `overrides installed version`); для двох увімкнених копій з одним `name` модуль хуків реєструє лише перша завантажена (вкладка Errors у `/plugin`), а місце теки dev-mods у цьому порядку не документовано (docs/plugins/loading.md). Тож не тримати маркетплейсну копію разом з dev-mods; для розробки надійніше `claude --plugin-dir mods/<mod>` на старті.

<a id="p58"></a>
58. **`$.process.run`, схоже, обривається хостом за ~30 с** (2.1.296, термінал, живий прогін PL_AUD_CTX_P12, `.dev_flow/cache/live-test/audit-p12-results.md`; не підтверджено документацією, точну межу не виміряно). Обгортка `sh`, що спала 30 с, закінчила сон і зробила `exec`, але рядка `sh exited` у журналі `--debug` не з'явилося, а виклик мода завершився без виводу; з затримкою 12 с — звичайний вивід. Тож довгий процес не тримає мод вічно, але й результату не дає: розраховувати на його завершення, а не на вивід. Лічильники викликів у журналі фільтрувати за `(context-editor)` — інші плагіни (`cc-plugin-telemetry`) теж запускають `sh` з двома аргументами.

<a id="p68"></a>
68. **`Read` поза робочим каталогом і `tool.check`** (2.1.296, `claude -p`, haiku, живий прогін фази 34, `.dev_flow/cache/live-test/phase34/`). Без `bypassPermissions` `Read` файлу поза `cwd` (напр. `~/.claude/context-editor/<session>/…`) хост відхиляє: «Claude requested permissions to read from …, but you haven't granted it yet» (`permission_denials`); у терміналі — питає людину. У `cwd` — дозволено, і в субагенті теж. `$.session.cwd()` дає робочий каталог сесії. Плагін може сам дати вердикт хуком `tool.check` (`{ tool: 'Read' }` → `{ decision: 'allow' }`; `next(e)` — вердикт хоста), не перевірено живим. Каталог, що ігнорує сам себе: `.gitignore` із `*` усередині — `git status` його не бачить, `.gitignore` проєкту без змін.
