# Моди Claude Code: поведінка хоста, яку треба знати

## Applicability Boundary

- **when_to_use:** пишете або змінюєте мод у `mods/` — хуки подій, виклики `$`, тести, живі сценарії.
- **when_not:** класичні хуки `settings.json` (команди оболонки) — інший механізм.
- **version_or_context_scope:** Claude Code ≥ 2.1.295 — старіші версії не підтримуються (рішення розробника 2026-10-09); пункти 1–15 перевірено на 2.1.294, 16–36 — на 2.1.295, інтерактивно й у stream-json; 37–38 — на 2.1.295 лише в stream-json, 39 — у `claude -p`; після оновлення хоста факти нижче перевірити заново (типи в `.claude-plugin/types/claude-code/index.d.ts`).
- **promotion scope:** `candidate` — підтверджено одним модом (`context-editor`).

## Context

Типи хоста описують контракти, але кілька важливих поведінок видно лише наживо. Кожен пункт нижче коштував раунду налагодження або рев'ю в задачі `task_C_CTX`.

## Key Concepts

- **Хук — `($, e, next)`.** Без виклику `next` хук відповідає сам; `next({...e, x})` переписує вхід. Модуль не має Node і DOM — усе через `$`.
- **Валідатор модуля** (`claude plugin validate`) вимагає, щоб `$` передавався лише у функції, оголошені на верхньому рівні того самого файлу; замикання всередині хука можуть викликати `$.x.y()`. Шаблони `tool.call` з `${...}` у матчері дають `tool=?` — матчер пишіть рядковим літералом. Одну подію модуль може зареєструвати без матчера лише раз: два `on('session.compact', …)` без матчера валідатор відкидає («registered twice without a matcher») — об'єднуйте їх в одному хуку (перевірено на 2.1.295).
- **Хуки, що можуть відмовити** (`tool.call`, `prompt.submit`, `session.compact`, …), мають мати `.catch`; без нього збій хука пропускається і подія йде далі, як без хука.
- **Тести** — `claude plugin test <mod>`, файли `tests/*.test.ts`, набір `claude-code/testing`. Імітувати весь `$` дорого: логіку виносимо за порти (див. `QueueIO`, `CompactionIO`, `FlushIO`, `HandoffIO`) і тестуємо як чисті функції.
- **Типи без глобального `tsc`:** `npx -p typescript@5.6.3 tsc -p <tsconfig>` з типами з `.claude-plugin/types/` (генеруються хостом при завантаженні мода).

## Usage in This Project

- Застосування правок контексту через `session.compact`: `mods/context-editor/hooks/compaction.ts`, зв'язування — `mods/context-editor/hooks/register.ts`.
- Запуск компактизації командою `$.command.run({ command: 'compact', args: MARKER })` з відкладеної дії після `turn.complete` у тому самому плагіні: `mods/context-editor/hooks/flush.ts`; засів очищеної сесії (`/clear`, потім `/compact` з HANDOFF_MARKER): `mods/context-editor/hooks/handoff.ts`.
- Живий прогін: окремий `claude --plugin-dir …` у tmux (скрипт-драйвер у scratchpad сесії), журнал — `claude --debug`, `~/.claude/debug/<session>.txt`.

## Pitfalls

1. **Плагін не бачить власної компактизації `$.session.compact()`.** Для прямого запиту з плагіна хост пропускає хуки цього самого плагіна («skipped: re-entry»), і запускається справжнє підсумовування; у неінтерактивному хості прямий запит відхиляється взагалі (пункт 18). Компактизацію, яку плагін запускає командою `$.command.run({ command: 'compact' })`, обробляють і його власні хуки (пункт 19).
2. **Не чекати `$.prompt.submit` у хуку `session.compact`.** Виклик завершується, коли стартує хід, а хід чекає кінця компактизації — взаємне блокування («Running PreCompact hooks…» без кінця).
3. **Відмова промпту — це `{ drop }`, а не виняток.** І `next(e)` у `prompt.submit`, і `$.prompt.submit` резолвляться з `drop`; перевіряйте поле.
4. **`session.compact` можна лише між ходами**: під час ходу виклик відхиляється — повторюйте після `turn.complete`.
5. **Рядки, повернуті з `handle`, після межі компактизації посилаються на старі батьківські рядки.** Рядки з результатами інструментів перезбирайте без `handle`, якщо в них немає медіа.
6. **Рядок без `handle` хост будує лише з тексту і блоків інструментів** — thinking-блоки й медіа в ньому зникають; `toolResults[].result` ігнорується (блок зображення там не допомагає). `handle` з іншої сесії (напр. до `/clear`) хост мовчки вважає відсутнім. `$.session.append` блоків зображень від плагіна не приймає. Перевірено на 2.1.295.
7. **`--resume` і компактизація від обробника (2.1.295).** Завантажувач іде по `parentUuid` від останнього рядка; `compact_boundary` (`parentUuid: null`) зупиняє обхід, тож текстові правки, чиї відповіді перезібрано цілими, переживають відновлення. Оригінали повертаються двома шляхами: (а) копія рядка, поверненого з `handle` (особливо медіа-`tool_result`), має батька до межі (пункт 5) — і все до останнього такого рядка вантажиться з оригіналів; (б) рядки асистента до межі з тим самим `message.id`, що й рядок, повернений з `handle`, підтягуються разом зі своїми результатами — `tool_use` дублюються, повертаються й вилучені виклики тієї ж відповіді. Засіяна після `/clear` сесія (рядки без `handle`) переживає відновлення завжди. У відновленому процесі `$.session.messages()` — завантажений ланцюжок (з дублікатами), а не «оригінали + копії».
8. **`/clear` і `/resume` у тому самому процесі змінюють `session_id` без `session.start`** — стан, прив'язаний до сесії, перевіряйте перед кожною операцією.
9. **`$.fs.write` і `$.fs.read` мають межу 4 MiB**; великі файли пишіть через `$.process.run(['sh','-c','umask 077 && cat > "$1"','sh',path], { stdin })`. `$.fs` не задає права доступу — `chmod` через `$.process.run`.
10. **`$.session.messages()` і `{ as: 'api' }`** віддають до 4096 останніх рядків/повідомлень; медіа видно лише в API-поданні.
11. **`$.tool.list()`** показує інструменти поточного процесу — так один плагін перевіряє, що інший завантажений саме тут.
12. **`.catch` має бюджет ~1 с**: не чекайте в ньому довгих ланцюжків — відповідайте одразу, решту робіть у фоні.
13. **`$.session.messages()` повертає весь транскрипт, разом з рядками до межі компактизації**: після компактизації від обробника старі рядки йдуть першими, далі їхні копії. Позначки межі в `SessionMessage` немає, і `session.append` рядків компактизації не бачить; `{ as: 'api' }` дає лише те, з чого збирається наступний запит. Вхід `session.compact` (`e.messages`) — лише хвіст транскрипту після останньої межі (і для `/compact`), а повернені рядки стоять у наступному читанні суцільним блоком з тими самими відбитками: на цьому стоїть межа поточної розмови редактора (SP_CTX_DEC_07). Перевірено на 2.1.295.
14. **`$.tool.register` обрізає `description` до 2048 символів** і пише про це в TUI; важливе ставте на початок опису.
15. **Медіа від вбудованого Read не буває великим**: зображення понад ~0.5 МБ він перекодовує в JPEG, а великий PDF (4.6 МБ) віддає сторінками-JPEG, не блоком `document`; малий PDF приходить блоком `document` з `source.type = base64`. Тестувати багатомегабайтний `stdin` треба через інший шлях (напр. архів кількох медіа одним пакетом).
16. **`$.command.run` запускає вбудовані `/resume <id>` і `/clear`** (`/resume` — лише в інтерактивному хості, див. 18) — з відкладеної дії після `turn.complete` (`$.clock.after`), не з хука, якого чекає хід (хост відхиляє з поясненням). За типами хоста команда стає в чергу і виконується, коли сесія вільна: виклик посеред ходу чекає його кінця, а відмова (невідома команда, хук, якого чекає хід) остаточна. Перемикання дає `session.end` з `reason`, але не `session.start`; невдалий `resume` (невідомий id) резолвиться `{}` без помилки — успіх перевіряйте за `$.session.id()` до і після. Перевірено на 2.1.295.
17. **Транскрипт сесії — `~/.claude/projects/<cwd з не-буквено-цифровими символами → '-'>/<id>.jsonl`, API для шляху немає.** `--resume` приймає зібраний поза хостом файл; обов'язкові поля рядків `user`/`assistant` — `type`, `uuid`, `parentUuid`, `timestamp`, `message`; модель бачить лише `message.content` (`toolUseResult` — для інтерфейсу). Без `timestamp` — «No conversation found», а розірваний ланцюжок `uuid`/`parentUuid` дає **тиху** порожню розмову. Деталі й збирач — спайк `docs/context_editor_session.spike.md`, `.dev_flow/cache/session-transcript/`.
18. **Неінтерактивний хост (VS Code, SDK, `-p`) — інший набір можливостей.** VS Code запускає `claude --input-format stream-json --output-format stream-json`. Там `/resume` немає в `$.command.list()` (`local-jsx` без `supportsNonInteractive`), і `$.command.run({ command: 'resume' })` відхиляється: «no command named /resume in this session»; `clear` і `compact` є. `$.session.compact` відхиляється завжди: «not available in a headless (-p / SDK) session yet …». У звичайному `claude -p "<prompt>"` після останнього ходу будь-який `$.command.*` дає «no session is bound in this process». Перевірено на 2.1.289 і 2.1.295.
19. **`$.command.run({ command: 'compact', args })` — компактизація, що працює всюди**, у тому числі в неінтерактивному хості. Обробник бачить `trigger: 'manual'` (не `'plugin'`) і `instructions` = `args`; хуки самого плагіна-ініціатора **не** пропускаються (пропуск «re-entry» з пункту 1 — лише для `$.session.compact`). Рядки команди `/compact <args>` і «Compacted» потрапляють у контекст моделі; хук `session.append` не може їх відхилити (`door=command`), а переписати вміст може лише в stream-json — у TUI ці рядки оминають `session.append` (пункт 24). `{skip}` обробника в stream-json видно як `result` «Not compacted · <reason>». Перевірено на 2.1.289 і 2.1.295.
20. **Засів очищеної сесії компактизацією.** Після `/clear` вхід `session.compact` — один рядок (сама команда `/clear`); обробник може повернути довільні рядки з парами `tool_use`/`tool_result`, модель їх бачить. Хост пише `compact_boundary` з `parentUuid: null`, далі повернені рядки (асистент — `model: "<synthetic>"`), і `--resume` такої сесії показує саме їх. Рядки без `handle` втрачають медіа й thinking (пункт 6). Деталі — спайк `docs/context_editor_handoff_long.spike.md`.
21. **Після вбудованої `/compact`** `{ as: 'api' }` починається з підсумку («This session is being continued…»), далі копія останнього тексту асистента і повідомлення `user` з `<system-reminder>`, куди хост знову вкладає нещодавно прочитані файли; сусідні `user` не злиті. Текст підсумку містить шлях до старого транскрипту («read the full transcript at: …/<id>.jsonl»).
22. **Команди, які запускає плагін (`$.command.run`), не породжують подій ходу** — ні `prompt.submit`, ні `turn.start`/`turn.complete`, для `/clear` і `/compact` в обох хостах; `command.run('compact')` завершується після відповіді обробника, `command.run('clear')` — коли `$.session.id()` уже новий. Лічильник ходів людини від них не зсувається. Перевірено на 2.1.295.
23. **Черга команди залежить від походження таймера, а не від моменту виклику.** Таймер, створений у хуку `tool.call`, хост відхиляє і через секунди («called from a tool.call hook…»); з опитувача, запущеного в `session.start`, команда стає в чергу і виконується після кінця поточного ходу (перевірено наживо); для таймера з паузи після `turn.complete` те саме випливає з типів хоста («queued and run once the session is idle»), наживо посеред ходу ще не спостерігалось. Повідомлення людини посеред ходу вливається в цей хід (`prompt.submit` з `turnId` ходу), окремого ходу немає. Перевірено на 2.1.295.
24. **Рядки команди плагіна в TUI оминають `session.append`**: копії після межі компактизації і рядки `/compact <args>`, «Compacted» пишуться у файл без хуків (видно лише рядок поза ланцюжком `door=prompt` «/compact <args>»). У stream-json, навпаки, кожен повернений обробником рядок знову проходить через `session.append` з `origin { kind: 'plugin' }` — хуки нових рядків (автотегування) спрацюють на копії. Перевірено на 2.1.295.
25. **Власні хуки `prompt.submit` плагіна пропускаються для промптів, які він надсилає сам** (`$.prompt.submit`; у журналі «prompt.submit skipped: re-entry (the plugin's own code raised it)»). Один плагін не може додати контекст до власного промпту через свій же хук — текст треба класти в сам промпт. Перевірено на 2.1.295.
26. **У stream-json `command.run('compact')` завершується до того, як повернені рядки потрапляють у `$.session.messages()`** (з'являються ~50 мс потому); у TUI вони вже є в момент завершення. Читання розмови одразу після власної компактизації треба повторювати, доки рядки не з'являться. Перевірено на 2.1.295.
27. **У stream-json промпт людини проходить `session.append` з `origin` `unclassified`**, не `sdk` (у TUI — `composer`). Правила «це рядок людини» мають враховувати обидва. Перевірено на 2.1.295.
28. **`$.model.fork` дає форкнутому агенту інструменти**: він може їх викликати (кожен виклик відхиляється), і відповідь забруднюється — у промпті форку прямо забороняйте виклики. Перевірено на 2.1.295.
29. **Після `--resume` сесії з вбудованою `/compact` `$.session.messages()` починається з рядка-підсумку**; гаряче перезавантаження модуля скасовує його таймери `$.clock.after`. Перевірено на 2.1.295.
30. **Хост зливає рядки асистента з однаковим `message.id` (одна відповідь моделі) при побудові запиту — навіть через рядки з іншим id.** Якщо обробник компактизації перезбирає один рядок відповіді (синтетичний `message.id`), пізніший рядок тієї ж відповіді, повернений з `handle`, підтягується назад у раніше повідомлення; його `tool_use` втрачає сусідній результат, і модель бачить «Tool result missing due to internal error» (медіа в такому результаті теж зникає). Так в обох хостах і обома шляхами компактизації; `SessionMessage` не показує `message.id`. Правило: у відрізку між двома промптами людини, де є перезібраний або вставлений рядок асистента, перезбирати всі його рядки асистента з `handle` — і пізніші (злиття назад), і раніші (рядок thinking тієї ж відповіді, пункт 36). Батько до межі в копії рядка з `handle` (пункт 5) не шкодить у тому самому процесі, але після `--resume` тягне ланцюжок оригіналів (пункт 7). Перевірено на 2.1.295.
31. **Гаряче перезавантаження модуля — лише в терміналі й лише за зміни вмісту файлу** (`touch` не досить); у stream-json зміна файлу нічого не робить, доки не надіслати повідомленням `/reload-plugins` (новий екземпляр модуля, середовище процесу те саме). Перезавантажений модуль пише в транскрипт «<plugin>: reloaded (N hooks…)» і втрачає весь стан у пам'яті — і таймери (пункт 29), і прапорці на зразок довіри до власних файлів. Після `--resume` у stream-json журнал налагодження називається за тимчасовим id сесії; процес, відновлений з тим самим id, пише в той самий `~/.claude/debug/<sid>.txt`, що й інший процес цієї сесії. Перевірено на 2.1.295.
32. **Ідентичність процесу хоста** для мода: токен, записаний `$.env.set` (успадковують дочірні процеси — прив'язуйте до pid), плюс `$PPID` з `$.process.run(['sh','-c','echo $PPID'])`; обидва не змінюються при гарячому перезавантаженні модуля і нові після перезапуску/`--resume`. `ps -o lstart= -p $PPID` теж дає час старту, але `ps` є не скрізь (slim-контейнери, busybox). `$.session.usage().startedAt` і `$.session.id()` після `--resume` не змінюються. `$.env.get`/`set` приймають лише рядковий літерал (валідатор сканує назви). Перевірено на 2.1.295.
33. **Очищення старих результатів хостом** (2.1.295, з бінарника й живого прогону): після відмови API «context hint» хост замінює вміст старих результатів вбудованих інструментів (лишає 5 останніх) на `<persisted-output>…` або `[Old tool result content cleared]`, а сервер після ≥3900 с простою може застосувати `clear_tool_uses_20250919`. Блок і його `tool_use_id` лишаються — присутність id в `{as:'api'}` не означає, що модель бачить вміст. На ~186k токенів без цих подій усі результати лишались.
34. **Один модуль хуків на плагін** (2.1.295): друге `modules` у `hooks/hooks.json` валідатор відхиляє.
35. **Хук `session.compact`, що відповідає без `next`, ховає подію від плагінів, завантажених після нього** (порядок — `--plugin-dir`; 2.1.295).
36. **Модель з thinking пише одну відповідь кількома рядками з тим самим `message.id`: рядок лише з thinking, далі рядок з `tool_use`.** Якщо обробник перезбирає рядок виклику, а рядок thinking тієї ж відповіді повертає з `handle`, `--resume`/`/resume` за злиттям `message.id` (пункт 7б) повертає оригінальний `tool_use` разом із результатом — правка втрачається навіть у суто текстовій розмові. Коли в завантаженому ланцюжку дублюються `tool_use`, кожен запит процесу пише `[ERROR] ensureToolResultPairing: repaired missing tool_result blocks`. Перевірено на 2.1.295 (haiku з thinking за замовчуванням).
37. **Розмір рядків розмови без незмінної частини** (2.1.295, проба в неінтерактивному хості 2026-10-10): `$.session.usage().context.tokens` — увесь останній запит разом із системним промптом, схемами інструментів, інструкціями MCP, агентами, файлами пам'яті й навичками (~38k у терміналі з haiku, ~70k у VS Code). `$.session.usage({ breakdown: 'summary' })` дає `context.breakdown.categories`; рядок `name: 'Messages'` (`kind: 'used'`, власного `kind` немає — шукати за назвою, хоча типи радять розгалужуватись лише за `kind`, а не за `name`: назва може змінитися між версіями хоста, тож без рядка — запасна міра) = розмір запиту − незмінна частина, узгоджений з останньою відповіддю API і вже з локальною оцінкою рядків після неї. Хук `tool.call` після `next` бачить `Messages` без результату поточного виклику. Ціна: `summary` 23–87 мс, без запитів до API; звичайний виклик 1–3 мс. `$.clock.now()` повертає Promise — `await` перед відніманням. Поки моделі ще не відповідали (свіжа сесія, щойно після компактизації), `tokens` відсутній.
38. **Промпт розширення після кінця ходу без команди** (2.1.295, проба в неінтерактивному хості з потоковим входом 2026-10-10): у `turn.complete` поле `e.answer` — фінальний текст ходу; `$.prompt.submit({ text })` з `$.clock.after(300, …)`, запланованого в `turn.complete`, без жодної `$.command.run` перед ним, запускає новий хід (результат `{ text, origin: { kind: 'plugin', … } }`, далі звичайні події ходу). В інтерактивному терміналі не перевірялось.
39. **Плагін з function hooks може мати власні навички** (2.1.295, проба `claude -p` 2026-10-10): тека `skills/<name>/SKILL.md` поруч із `hooks/`; валідатор її приймає, агент бачить навичку в переліку як `<plugin>:<name>` з описом із frontmatter; повний текст — лише коли агент її відкриє.
